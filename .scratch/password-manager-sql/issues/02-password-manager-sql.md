# 02: Switch the password manager to automatically provisioned SQL storage

**What to build:** A User signs in and immediately manages secrets in the database explicitly provisioned by the password-manager application. Load, save, delete, Refresh, and reopen-after-reload work without filesystem/database selection or manual creation. Recovery and session teardown retain existing data-loss and confidentiality safeguards.

**Blocked by:** 01 — Provide explicit authenticated SQL database access.

**Status:** ready-for-agent

- [ ] Put default database resolution, application-chosen logical identity, explicit creation, and schema initialization/checks in an application-owned startup module. Use the generic identity/lifecycle contract from ticket 01; neither the SDK nor collection adapter chooses or creates the default.
- [ ] Initialize/check schema repeatably and transactionally, including its version state. Use one secrets table containing a secret ID and serialized validated record. Keep ordering in the existing TanStack live query; do not normalize nested fields or add speculative SQL indexes/filtering.
- [ ] Replace filesystem persistence with a focused SQL collection implementation receiving an already resolved database and narrow structural Storage SQL interface. Keep the official TanStack Svelte binding, collection mutations, optimism, authoritative reconciliation, Refresh, and cleanup. Do not build a generic SQL collection framework or couple the adapter to the concrete SDK.
- [ ] Preserve Secret schema validation, favorite/name ordering, additional URIs and match modes, custom fields, unedited notes, timestamps, and existing history. Changing the password appends its previous value to history; validation rejects invalid drafts before writes.
- [ ] Deliver load/save/delete/Refresh together; remove manual filesystem selection/open/create controls and obsolete app-specific filesystem wiring, fixtures, and documentation. Preserve generic filesystem capabilities and other consumers; do not retain compatibility wrappers or a second write path.
- [ ] Distinguish preparing, loading, empty, ready, malformed, unavailable, deleted, and denied states. Offer explicit safe provisioning retry without silently resurrecting a deleted database or replacing inaccessible acknowledged data with an empty database.
- [ ] Report mutation success only after persistence and authoritative reconciliation. Reconcile rejected writes, retain editable drafts where safe, and identify uncertain outcomes without blind replay or false success. Failed reconciliation hides untrusted records and requires explicit recovery.
- [ ] Refresh reloads external additions/updates/deletions, closes stale drafts on success, and cannot conflict with active writes. Failed or malformed snapshots never publish a partial or falsely empty vault. No polling, automatic reconnect, or offline mutation outbox.
- [ ] Immediately clear records/drafts and dispose dependent queries/collections on sign-out, identity change, route teardown, or SDK retirement. Ignore late provisioning/read/write/Refresh outcomes. Preserve the current editor through same-identity renewal; distinguish Storage failures from terminal IdP failures.
- [ ] Reuse mounted application workflow tests with the real SDK, OIDC/Storage clients, collection, and official binding against controlled transport. Cover first sign-in, automatic provisioning, ready-empty state, returning visits/reload, schema checks, explicit provisioning retry, CRUD/metadata/history/order, external changes/Refresh, malformed records, rejected/uncertain writes, and session changes during pending operations.
- [ ] Document that old filesystem records remain untouched and are not imported or used as fallback. Do not add implicit migration, dual-write, or resource deletion. Keep Device selection and replication permissions separate from app provisioning.
- [ ] Document that SQL does not add end-to-end encryption, secure erasure, production vault qualification, or concurrent-edit protection. Keep decrypted secrets out of browser persistence and logs; use non-sensitive test records only.
- [ ] Run focused tests, type checks, production build, and applicable formatting/lint checks. Qualify actual IdP exchange, automatic creation, SQL CRUD, reload, Node restart, denial, and recovery when a running Installation is available; explicitly report unavailable manual qualification. Test replication separately only if claimed.
