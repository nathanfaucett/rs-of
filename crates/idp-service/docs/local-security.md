# Local identity, policy, signing, and grants

Every Node executes OAuth and identity operations against its own persistent trusted IdP state. There is no authority designation, promotion or freshness lease. Bundled permissions use local Management; independent deployment uses its authenticated HTTPS evaluator. OAuth configuration rejects the retired `role` field. Missing, corrupt, conflicted, unapproved, or locally revoked evidence still denies.

## Owner boundaries and administration

Authenticated IdP HTTP administration binds the verified User subject to the exact service audience, action, and target. Application-scoped requests must also match the actor's locally known client Application. `LocalPermissions` evaluates Management's own persistent store; IdP never reads Management repositories. Unified composition shares this evaluator with the local Management context. Independent IdP uses its configured HTTPS Management relationship rather than opening another owner's store. Missing policy/grants or evaluation errors deny before owner mutations. The in-process owner service and repository APIs are trusted composition seams, not alternative unauthenticated administration endpoints.

Bundled Management calls IdP locally for bearer/active-User validation without an introspection Client or HTTP self-call; independent Management uses authenticated HTTPS. If that local context is unavailable, authentication still fails closed. Removing remote authority dependence does not mean operating without a functional local identity/policy context.

## Independent local signers

`NodeSignerBinding` identifies the local membership, signer key, and endpoint. `prepare_node_signer` persists independent private material in the local private-key repository and returns only a public JWK; it does not approve membership. Issuance requires exact current public signer approval and retained private capability, not an IdP Device record. Management independently owns transport Device approval; a separate injected transport endpoint need not equal the IdP signer binding endpoint.

Each operation rechecks persistent signer membership, signer, conflict, issuer, approval, and expiry state. Loading private material derives the public point and compares it with the approved JWK. A missing local secret never triggers implicit replacement during issuance. JWKS publishes approved Node signers only, not User/Client authentication keys. JWT signature algorithm and key metadata are ES256K/secp256k1, not EdDSA. Signed access/refresh/ID tokens also carry a required `principal_key_id` binding, independent of the Node signer ID, so locally learned authentication-root rotation/revocation rejects tokens bound to an old root. Tokens without the current binding are rejected; there is no legacy-token fallback. The token subject is independently resolved to a locally active User/Client and authentication root; a transport endpoint or signer key is not the Principal. Client, scope, use, issuer, audience, and lifetime checks remain mandatory.

Valid issuance requires an explicit local preparation/approval/configuration sequence:

1. Allocate stable signer member/key IDs and Canonical Issuer binding; keep Management Device ID and actual transport endpoint distinct.
2. Call `KeyService::prepare_node_signer` with that `NodeSignerBinding` in the Node's private-key namespace. Exact retry returns the same public key; preparation is not membership approval.
3. Through authorized setup/join, persist Management Device approval separately from IdP public membership/signer records (`DbReplicaSignerRepo::enroll` is the signer owner composition seam). Public approvals do not provide private capability.
4. Persist `OAuth2Config.local_signer`, endpoint identity, and the secure private-key namespace/material; reconstruct the runtime with those same values. Issuance only loads matching approved material, never implicitly prepares or replaces it.

Production owner provisioning now calls `prepare_node_signer`, and purpose-bound join prepares and retains an independent signer before approval. Unified public readiness checks current owner trust and signing capability; desktop projects current shared-worker/owner readiness and the public login Client into one target-bound observation; no Device-dismissal marker participates. Preparation, an approval receipt, a running listener, or a completion marker alone is not readiness. Missing binding/trust/private material still fails closed without automatic replacement. [Current API boundaries](../../../docs/api.md#setup-join-and-readiness) distinguish these delivered seams from acceptance: **rendered GUI approval/completion and two-profile GUI offline restart remain unverified**, as recorded in [current qualification limits](../../../docs/operations.md#qualification-boundary). Secure-store/platform and full-host qualification remain downstream.

Owner-local `verify_token_principal` checks an ID token's signature, issuer, lifetime and signed Principal root against locally trusted state, including learned root rotation/revocation. ID tokens are not accepted as access tokens. This seam is not a complete relying-party OIDC validator (audience/nonce/session checks are the consumer's responsibility), nor a way to make revocation effective at an unaware offline relying party. ID-token profile serialization emits the canonical subject once, without a duplicate flattened `sub`.

Principal setup captures an explicit `metadata-root` mode, actual entity/root UUIDs and canonical path ancestry. Exact retries verify the captured initial root and the current active root without consulting the private provider. Root rotation changes the active metadata identity, not the subject or Node signer. Missing/corrupt captures or metadata deny without replacement. Older setup records without the discriminator are not inferred from null JWKs or migrated: provisioning refuses them unchanged. Explicit reset consults the private provider for captured ancestry and every retained entity-key path and its ancestors, including revoked/expired metadata rows. A null public JWK does not prove that a private write was never attempted. Unexpected private material under a metadata-root capture or an uncertain provider read denies before evidence is discarded. Legacy private-attempt cleanup retains the durable resetting fence and verified deletion; all secret cleanup completes before entity-key metadata is removed. Ordinary metadata-only setup/retry remains provider-free, but explicit reset is not.

`DbReplicaSignerRepo::trusted_signers` validates current IdP signer membership/conflicts without Device reads. Management's Device repository supplies current conflict-clear endpoint/owner/approval/revocation evidence separately, including duplicate endpoint denial and active-User checks. Approved endpoints need no individual IdP signer; current exact Management policy is still required for their use. Neither owner substitutes for the other.

## Public security exchange contract

`PublicSecurityTable::columns` is an explicit **projection** contract. It does not authorize exporting opaque whole-table/whole-row CRDT documents that may contain excluded fields or history. `permits_record` requires every projected column exactly once, including explicit nulls for nullable columns, and validates SQL primitive types, non-null columns, UUID identities (UUIDv7 primary IDs), public JWK text/point validity, and grant hash shape. Unknown fields, private JWK parameters (including private scalars embedded in JSON text), and raw code/token values masquerading as hashes are rejected. Column coverage/types are tested against the actual migrated schemas, including consent `scope`/revocation/details and authorization-code User/details fields. This is a complete SQL-shaped projection, not a partial update format or model/API JSON format. SQL indexes, foreign-key/dependency integrity, domain state semantics, provenance, actor permissions and actual import/apply checks are additional requirements, not established by this predicate (02/03).

Allowlisted IdP data includes public Users, Applications, client registrations without secrets/verifiers, public authentication-key metadata, approved signer membership/trust, consent metadata/revocation, and hashed authorization-code/refresh-grant lifecycle state. Credentials, password verifiers, client secret verifiers, enrollment secrets, private signers/master keys, raw passwords, raw codes, and raw tokens are excluded. Receiving public client data does not provide confidential-client authentication capability; required local credential material must be provisioned locally. Management separately allowlists public Devices, roles, permissions, role-permission links, User-role assignments and selection policy in its own store.

Transport trust resolves the **authenticated connection endpoint** through current Management Device/owner state, not IdP signer membership. A wire string, actor claim, configured JWK or successful pairing is not approval/resource authority. Repeat exact local admission/permission checks before actual application, including existing connections. Full-Node Join separately validates its exact approved signer tuple. See [setup/Join contracts](../../../docs/api.md).

## Local consumption and reconnect

Authorization codes and refresh grants contain hashes, never raw grant credentials. Conditional local consumption/rotation has one concurrent local winner and persists across database reopen. Wrong client, redirect/PKCE, scope, Principal, signer, or signature evidence denies; authorization-code redemption checks local signing capability and issuance inputs before consumption.

Two disconnected Nodes with the same locally trusted grant may each consume it. Their independent successful decisions are accepted; neither a designated consumer nor a global lock is introduced. Different locally signed replacement tokens do not imply global single use. Reconnect cannot undo tokens already issued during a partition.

Unresolved security-row conflicts deny authentication/authorization/issuance. Authorized owner-local conflict resolution is audited and cannot resolve consumption or revocation back to null; conflicting lifecycle fields require a retained integer timestamp. Learned revocation or consumption prevents later local work. Other security conflicts require explicit authorized resolution, not silently trusting last-writer-wins ordering. The authenticated record import/reconciliation adapter and live reconnect/revocation integration remain downstream qualification, not guarantees inferred from CRDT convergence.

## Evidence boundaries

Domain tests use real owner repositories and services, separate local stores, and native database reopen. The persisted-binding test serializes configuration to disk, drops the original services, reconstructs all owner repositories from native database reopen, and exercises real OAuth refresh issuance/validation and durable replay denial over a second reopen. It retains a test private-key store across reopen; it does not prove OS keyring behavior across process restart. Partition tests deliberately demonstrate two local refresh winners and subsequent local replay denial. The HTTP administration test retains actor/action/target/audience/impersonation denials while proving IdP administration continues after the Management HTTP listener stops, because local policy remains available. Current integrated HTTPS/Create/Join and offline-reopen evidence is recorded in [operations](../../../docs/operations.md#qualification-boundary), separately from native GUI/provider/platform acceptance.
