## Ranked findings

1. **P1 — Identity policy disappeared from security synchronization/bootstrap.** `crates/unified-server/src/security_sync.rs:147–165` builds `policy-identity` by filtering `PUBLIC_DEVICE_TABLES` for identity-policy names. That constant contains only `devices`, `device_selection_policies`, and `device_resource_selections` (`crates/device-service/src/security_sync.rs:3–7`), so the identity session is always empty. IdP's public table list also excludes roles/permissions (`crates/idp-service/src/security_sync.rs:298–311`). Consequently grants/revocations cannot propagate; normal Device-context sync additionally attempts an empty SQL batch during schema validation (`security_sync.rs:267–292`). Bootstrap uses the same broken sessions (`security_bootstrap.rs:597–649`); standalone local Join likewise imports neither identity policy nor its grants. Existing peers can retain stale authorization, and fresh joins cannot acquire required grants. **Fix:** restore an explicit identity-policy history allowlist/session and its column/candidate validators, separate from Device history; test cross-node grant, revoke, and fresh/offline Join—not just shared-handle HTTP.

2. **P1 — Remote IdP reset deletes shared key rows.** `crates/idp-server/src/independent_reset.rs:139–155` now constructs a remote `OwnerProvisioner` and invokes the old local-owner `delete_local_secrets`. That helper unconditionally calls `delete_by_entity_type_and_id` for captured entities, including metadata-only references (`node_provisioning.rs:1038–1062`); the repository executes SQL `DELETE FROM keys` (`crates/idp-service/src/replica/key_repo.rs:191–206`). Resetting the remote Create consumer therefore removes administrator/Client key metadata from the shared identity owner, even while other consumers still use those records. The remote acceptance only resets Device, so it misses this path. **Fix:** separate protected/local inventory cleanup from public metadata retirement; remote consumer reset must never delete shared rows. Assert complete key-row preservation and continued source operation across IdP reset.

3. **P1 — Default independent local Create/Join is no longer provisionable.** `crates/device-server/src/independent_create.rs:577–584` now requires `identity_client(config)` to seed administrator policy; independent runtime construction also requires it (`independent_join.rs:105`). With ordinary fresh/default configuration, both identity selectors are absent, and `database_client.rs:28–46` reaches `provisioning.rs:156–169`, which requires an existing explicit identity file. Nothing in the independent worker supplies this connection. The retained local acceptance fixture still uses exactly that default configuration (`crates/unified-server/src/owner_composition_tests/create.rs:121–137`). Setup accepts the operation and creates protected/local state, then cannot finish. Merely pointing another process at IdP's open redb file is not a shared-query solution. **Fix:** wire the shared identity connection through independent setup for supported local deployments; qualify nonremote Create/Join/reopen, not only the remote fixture.

4. **P1 — Local independent IdP still sends permission evaluation to Device's removed route.** `crates/idp-server/src/independent_create.rs:253–260` sets the nonremote evaluator base to `intent.device`. `build_independent_idp` injects direct permissions only for remote identity configurations (`independent_join.rs:36–40`). Thus local permission checks call `<device>/permissions/evaluate` through `management_permission_client.rs:95–110`, but Device no longer registers that route (`crates/device-server/src/router/openapi_router.rs:48–72`); only Management does. Even after fixing finding 3, local IdP administration and signer enrollment fail unavailable instead of evaluating the grants in identity. **Fix:** use the injected identity client for local permission evaluation too; remove obsolete Device-as-Management evaluator wiring and test an authorized local independent administration/Join action.

### New private Unix SQL seam: access, lifetime, deployment

- `idp-server/src/independent_identity.rs` exposes full identity-domain SQL, **not OAuth-authorized/per-table SQL**. Its security boundary is the OS account. `api/src/independent_setup.rs:103–113` creates/checks the parent setup-host directory and takes an exclusive `operation.lock`; `api/src/setup_files.rs:69–78,102–118` enforces owner-only permissions, euid ownership, and nonsymlink ancestry. This protects the unauthenticated socket from other unprivileged accounts. Processes under the same account already have access to the local owner files/protected setup inventory; they are explicitly trusted by this deployment model. Public disclosure of the socket path does not grant traversal. No remotely reachable TCP SQL listener was added.
- `IndependentCreateControl::peer` checks the HTTPS-discovered owner and exact retained operation before Device accepts the socket fact. The socket is served from the already-open IdP `Arc<Database>`, not a second opener. The setup-host lock spans serving and shutdown, preventing a concurrent reset or second cooperating host from replacing a live socket. A retained socket is removed for restart; a nonsocket/symlink at that exact name is refused. Normal shutdown removes the socket; after a crash the next host can replace the stale socket, and stopped-host reset can remove retained local setup state. No new concrete auth/access or reset-lifetime defect found.
- Remote identity owners yield no local database to the socket task; Unified never starts this listener. Local Device requires its local IdP host to remain running. Separate machines/accounts and non-Unix deployments need explicit remote SQL, as the updated spec/docs say. A Unix socket also has the platform pathname-length limit; no cross-platform/container/native-provider rollout qualification is implied.
- The 60-second timeout encloses socket connection/schema validation, not the preceding `wait_peer` discovery loop. That loop can keep waiting until shutdown while IdP is unavailable. Do not read ticket05's bound as a 60-second end-to-end setup/reopen guarantee; I did not establish an introduced functional blocker from this existing peer-wait pattern.
