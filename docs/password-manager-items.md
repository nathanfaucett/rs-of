# Password manager typed items

Implemented by ticket 05. The field authority is [personal-json-v1](password-manager-json.md); the evidence limits remain in [the reference baseline](password-manager-reference.md). Ticket 06 adds read-only detail and protected actions. Ticket 07 adds Secure Note creation and editing. Ticket 08 adds Card creation, editing, and protected details. All five kinds—Login, Secure Note, Card, [Identity (ticket 09)](password-manager-identity.md), and SSH Key—have editors and type-specific details. These editors do not implement autofill, import, or export.

## Model and interfaces

`apps/password-manager/src/lib/secrets/secret.ts` exports `SecretSchema`, a strict Valibot variant on `kind`, and the `Secret` union. It also exports each type and schema: `Login`, `Card`, `Identity`, `SecureNote`, and `SshKey`. Narrow on `kind` before reading type-specific properties. There is no parallel generic required-password schema or legacy writer.

Type fields are flat within each encrypted record. The names are local names, not Bitwarden wire objects:

| JSON kind / number | Local `kind` | Type-specific mapping                                                                                                                                                 |
| ------------------ | ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Login / 1          | `login`      | `login.password` → `secret`; `username`, `totp`, and ordered `uris` retain their names. All credentials are optional.                                                 |
| Secure Note / 2    | `secureNote` | `secureNote.type` → `type`, default integer `0`; body → common `notes`.                                                                                               |
| Card / 3           | `card`       | `cardholderName`, `brand`, `number`, `expMonth`, `expYear`, `code`, unchanged. All optional strings; no numeric coercion, brand restriction, Luhn, or date rejection. |
| Identity / 4       | `identity`   | All eighteen fields in the JSON contract retain their names. All optional strings; no country-dependent normalization.                                                |
| SSH Key / 5        | `sshKey`     | `privateKey`, `publicKey`, `keyFingerprint`, unchanged. Only `privateKey` must be nonblank; accepted text is not reformatted or checked as a key pair.                |

Common data: UUID `id`, nonblank `name`, optional `notes`, `favorite`, ordered `fields`, ordered `history`, `createdAt`, `updatedAt`, optional `deletedAt`, optional UUID/null `folderId`, and optional `importSource`. Dates retain their supplied ISO timestamp strings during transition; edits retain creation time and set update time. `passwordHistory[].password/lastUsedDate` maps to `history[].secret/changedAt`. No history truncation or deduplication occurs.

Optional scalar fields accept omission, null, and strings, including empty strings. The Login draft uses empty controls but retains an unchanged stored absent/null/empty value on save. Removing a previously stored password records the prior value in history. A new or changed nonempty password requires confirmation; removing one does not require an impossible nonempty confirmation. Cancel changes no stored value, including nested URI/custom-field edits.

URI `match: null` means inherited default and differs from explicit `domain`. The other local rules are `host`, `startsWith`, `exact`, `regex`, and `never`. Legacy omission becomes explicit `domain`, as the old reader required. No URI rule is executed by this ticket. Text and hidden field values can be null. Existing Boolean wire text is preserved, including old unset values; the future personal JSON importer must separately enforce its exact `"true"`/`"false"` input rule. Unknown keys, kinds, URI strategies, and custom-field variants block the complete snapshot; they are not stripped from persisted data.

`importSource: { format: "personal-json-v1", id: <nonblank external ID> }` is encrypted within the item and included in backups. This is the durable source-ID slot for ticket 17. It does not authorize destination overwrite. Import must allocate a fresh local ID, validate the whole file, compare source IDs and logical duplicates, and require the documented batch choice. No importer, duplicate index, plaintext hash, or bulk commit API is implemented here. `folderId` stores membership only; folder records and behavior remain ticket 12.

### Callers for ticket 06 and type tickets

- `createLocalSecretCollection({ vault })` accepts the full union. It calls `vault.prepareItems()` before loading a complete validated snapshot. Existing single-mutation acknowledgement and authoritative reconciliation remain. This is **not** an atomic batch importer.
- `createLocalSecretWorkflow({ vault })` exposes union `records`, `detail`, `open(id | null)`, and `dirty`. Selection stores only an ID; `detail` comes from the collection, not another item store. Opening is read-only. Its `edit(value = null, kind = "login")`/draft/save path accepts all five kinds. New Cards use `edit(null, "card")`. New notes use `edit(null, "secureNote")`; existing records determine their own kind. New Identity and SSH Key drafts use `edit(null, "identity")` and `edit(null, "sshKey")`. No kind is converted into Login.
- `EditableSecret = Login | SecureNote | Card | Identity | SshKey`, `EditableKind`, and `SecretDraft = LoginDraft | SecureNoteDraft | CardDraft | IdentityDraft | SshKeyDraft` cover all five kinds. `createSecretDraft(record, kind?)` and `constructSecret(previous, draft, id, now)` narrow directly on `kind`. They preserve metadata, unchanged absent/null/empty notes, and isolated custom fields; only Login has credentials and URI controls. Notes use subtype `0` and common `notes`, never a synthetic password. Only Login password changes append history. Transient TanStack virtual properties are stripped only when making a draft; durable records use strict validation.
- Public vault preparation: `await vault.prepareItems()`. Call it before typed writes and reads outside the collection. The low-level encrypted storage API still accepts serialized text for storage tests/recovery inspection; after preparation it validates the full typed item and matching ID. There is no old-format write path. `close()` retires the handle and releases its key reference. Late decrypted results cannot return through a closed handle.
- `exportBackup()` exports the current committed format. `exportTransitionBackup()` independently authenticates and exports the retained pre-transition version 1 file, if present. It does not depend on current records being valid; damaged recovery metadata is rejected. The page provides both download actions, even when collection loading fails.

## Detail, editing, and protected actions

Ticket 06 keeps one durable item authority: `SecretSchema` and the collection snapshot. `SecretDetail.svelte` takes `{ record: Secret, canEdit, onedit, onclose }`. It renders common notes, fields, dates, and history once, then narrows `record.kind` for all five kinds. Secure Note bodies use protected reveal/copy controls; Unicode, line breaks, and markup remain plain text. Dedicated Card, Identity, and SSH Key field components reuse the same durable union, collection, and protected actions. There is no plugin registry or parallel store.

### SSH Key items (ticket 10)

Use **New SSH key** to create a key without Login controls or a Login password. The existing strict `SshKeySchema` is the only durable field model: `privateKey`, `publicKey`, and `keyFingerprint` map unchanged from the verified JSON contract. Name and private key must be nonblank strings. Public key and stored fingerprint are optional strings. Unchanged omitted/null/empty values, notes, favorite, ordered custom fields, history, folder membership, import provenance, and creation dates survive edits. Only the selected item's update date changes. Key edits do not create Login password history.

Keys are opaque text. OpenSSH, PEM (including encrypted PEM), PuTTY-style text, arbitrary nonblank text, Unicode, multiline content, and accepted leading/trailing whitespace are stored without parsing or reformatting. Unchanged CRLF text also survives a save. These are storage representations, not claims that a key is well formed or usable. No key-pair matching, fingerprint derivation, algorithm check, decryption, key generation, SSH agent, passkey, or native integration is performed. Blank/missing/null/non-string private keys, non-string optional fields, and unknown record properties are rejected. Binary files, file parsing/import, and key-format validation are not supported.

Private key details use `ProtectedValue`: masked by default, explicit keyboard reveal/copy, fixed copy-error feedback, and no key-bearing diagnostics. The dedicated `SshKeyFields` editor also omits private key text from the DOM until **Show Private key**. It uses a plain multiline control with autocomplete, spellcheck, and capitalization disabled. A new editor instance resets reveal state. Public key and stored fingerprint use read-only plain-text detail/copy controls. Navigation, cancel, save, refresh, and lock retain the existing keyed-detail and retired-workflow cleanup. Clipboard and JavaScript memory limits are unchanged.

Evidence: `src/routes/ssh-key.test.ts` uses the mounted real page, workflow, collection, Chromium SQL/WASM, IndexedDB, and Web Crypto. Sixteen cases cover create/view/edit/cancel/save, exact multiline/CRLF and opaque representations, optional values, metadata/custom fields, isolated neighboring Login/Note/Card/Identity records, blank/malformed input rejection, masked reveal/reset, explicit successful/denied copy, write/readback failure, and late draft/copy/read/write/acknowledgement cleanup after lock. A complete mixed-type snapshot with folders and encrypted lock settings restores into clean storage after source storage is discarded, with exact logical data and encrypted records checked after reopen. All keys are deliberately nonfunctional synthetic text.

`scripts/check-ssh-key.mjs` extends the existing offline and backup browser checks: keyboard creation/reveal/edit/cancel/save, masked reset, exact fields after offline reload and new-browser-process startup with the server stopped, and clean-profile encrypted recovery. It adds no runtime dependency, network call, asset, storage format, or alternate writer.

`ProtectedValue.svelte` takes `{ label, value: string | null | undefined, protected?: boolean }`, protected by default. Password, TOTP seed, hidden custom fields, and history use the same control. Masked values are not inserted into DOM text, attributes, or input values. Null/absent values show Not set and cannot be copied; empty strings remain copyable. Reveal is explicit. Copy never requires reveal and catches unavailable/denied clipboard access with fixed, accessible feedback that cannot include rejected values or exception text. Values are plain text, never HTML or clickable credential-bearing URLs.

The detail subtree is keyed by the selected collection record. Leaving it, entering edit, cancelling, refreshing, or locking destroys revealed state and pending-copy feedback. Keep that boundary when extending details. No automatic clipboard clearing is attempted: browser clipboard APIs cannot atomically compare and clear, so even read-then-write can overwrite newer content. The copy and lock messages state that copied values can remain. Clipboard access, OS retention, secure JavaScript memory erasure, and compromised-browser protection are not guaranteed.

`LocalSecretEditor` remains the page's list/detail/editor owner. It exports `hasUnsavedChanges()` (dirty draft or pending collection work) and `retire()` (synchronous, idempotent UI/workflow cleanup). Item/new/refresh/delete navigation asks before discarding a dirty draft. Cancel explicitly discards the isolated draft and returns to masked details. Save waits for the existing collection acknowledgement, returns to details, and updates history only through `constructSecret`; notes-only edits and abandoned drafts add no history. Block-local editor bindings prevent late input events from reading a retired draft. Focus goes to the detail heading, edit name, delete confirmation, or New secret control as appropriate. Long pages stay top-aligned so controls remain reachable.

The page guards route/document navigation with unsaved/pending work. Manual Lock is never blocked by a write or backup and does not ask permission: it retires the editor, closes the vault, and warns that an already-sent write may have persisted. Unlock and verify before retrying. Late collection/read/copy results cannot restore the view. A session counter also rejects late backup downloads/errors after lock or unmount and closes late create/unlock handles after page destruction. No drafts, revealed values, or selected items are serialized into browser history, URLs, or persistent UI state.

## Unlocked search, filters, and sort

Ticket 11 adds `secrets/search.ts` and list controls in `LocalSecretEditor`. `searchItems(records, { text, kind, favoritesOnly, sort })` is a pure projection of the current unlocked collection snapshot. It returns a new array without changing records or keeping an index. The editor derives results from the workflow; result selection still uses `workflow.open(id)` and the existing dirty-navigation guard. Search and filter changes do not edit, save, or discard a draft.

Search is a trimmed, literal substring match within each allowed field. Both query and fields use NFC normalization and locale-independent lowercase. Search includes names, notes, custom-field **names**, Login/Identity usernames, and Login website text, regardless of stored URI match strategy. Passwords, TOTP seeds, history values, custom-field values, card numbers, identity identifiers, and SSH key material are not searched. All five defined union kinds support common search and type/favorite filters, even before their editors arrive. Records with `deletedAt` are always excluded from normal results. Folder membership composes before search/type/favorite/sort. Trash has a separate unfiltered view.

Default order is favorites first, then normalized name ascending. Explicit choices are name ascending/descending, recently updated, and recently created. Dates compare instants, not ISO string spelling. Date ties use normalized name ascending; every final tie uses ID ascending. Name comparison uses deterministic JavaScript string order, not locale-specific dictionary collation. Clear filters clears text, type, and favorite filters but retains the chosen sort. Missing optional fields do not match text. Loading/read-error feedback remains owned by the workflow; search controls are disabled until readable, read errors hide stale results, and retry keeps the filters. Empty results have a status message; result counts use a separate polite live region so they do not replace protected-action feedback.

Search state belongs to one mounted editor only. Retirement and unmount clear query/filter state and result references, hide controls, and dispose the workflow. Late refresh results cannot restore the retired view. No query or results are written to URLs, browser history, local/session storage, SQL, or a cache. There is no network dependency, new package, or storage/backup format change. This releases application references; it does not promise JavaScript memory zeroization.

Evidence: `src/lib/secrets/search.test.ts` mounts the real workflow/collection in Chromium with a synthetic vault adapter. It covers combined filters and clear, read-only navigation/no writes, all kinds, Unicode composition/case, optional data, allowed/excluded fields, deleted records, every sort and stable ID ties, acknowledged mutations and refresh, failed-read retry, retired late refresh, and 2,000 synthetic records without a timing claim. Storage assertions compare local/session storage, database registrations, and URL state; they are not a general storage security audit. `scripts/check-search.mjs`, called by `check-offline.mjs`, exercises keyboard controls, real SQL/WASM persistence, read-only result navigation, and unchanged UI storage with networking disabled and the server stopped. The existing lock, cold-start, and clean-profile encrypted backup checks still pass. The full app suite did not pass in this run; exact commands and failure limits are recorded in ticket 11.

## Trash and recovery

Ticket 13 changes normal **Delete** to an encrypted, persisted `deletedAt` update. **All items** and read-only details exclude deleted records. **Trash** is a separate, keyboard-accessible view with item names and deletion dates; it does not expose credential fields. No retention timer or automatic purge exists.

**Restore** removes only `deletedAt` and returns the same item ID, contents, creation/update dates, favorite state, fields, history, and import provenance. If folder membership cannot be resolved, restore makes the item unfiled (`folderId: null`). Restore checks the folder catalog: existing membership is retained, and only a missing folder becomes unfiled. Omitted/null memberships remain unchanged. Complete-snapshot validation rejects direct orphan writes; folder deletion unfiles trashed members before restore. Its atomic folder deletion must unfile both active and trashed members; do not make a loop of independent item writes appear atomic.

**Delete permanently** is available only in Trash and requires a separate modal confirmation. Cancel or Escape changes nothing and returns focus to the invoking control; initial focus is on Cancel. Permanent deletion affects only the selected trashed item. It is not secure erasure: SQL history, retained transition sources, browser storage, and earlier backups can still contain ciphertext or earlier item data.

Trash changes use the existing collection acknowledgement and complete authoritative snapshot reload. An unconfirmed write never produces success feedback. On failure or uncertain outcome, refresh and verify before retrying. Lock retires the workflow and removes decrypted Trash/confirmation state; an already-sent write can still persist, but its late result cannot restore the view or success feedback. Encrypted backups include Trash, with no backup format change.

## Versioned transition and recovery

SQL migration 3 appends `item_format` (default `1`) and `transition_backup`; migrations 1 and 2 are unchanged. New vaults start at item format `2`. Authentication/identity transitions remain separate. Unlock alone does not rewrite records. The collection prepares the format before exposing any records or enabling editing.

For format 1, preparation validates **every** decrypted record, nested field, date, and matching inner/outer ID. It builds Login records without changing IDs, logical dates, passwords, TOTP, notes, favorites, ordered URI rules, custom fields, history, or deletion dates. It also retains the original outer record timestamps. Malformed/unknown data stops the operation before staging; no partial subset is shown.

Preparation then makes an authenticated version 1 source backup and checks that the complete version 2 backup, including the source backup, fits the supported limit. It uses the same transactional staging and close/reopen/exact-readback verification as restore. The new database contains the complete converted set, original metadata/proof, item format 2, and the encrypted source backup. Only after durable verification does an IndexedDB transaction compare the original registry entry and publish the new database pointer. A registry readback is required before success.

The **original database is retained unchanged**. Registry `previousDatabaseName` prevents a retained named legacy source from being registered again as another vault. Staging names are not auto-discovered. No error path deletes the original, guesses that a rejected write rolled back, or reports unconfirmed conversion as saved. A failed or unconfirmed publication can leave either the original pointer or a complete converted pointer; reopen and verify before retrying. Retry validates the authoritative published format and does not convert it twice.

Web Locks serialize preparation and local writes by vault ID across handles/tabs. A stale handle resolves the published database before writing, checks its bound metadata/proof, and cannot write into the retained source. Other old application builds do not participate in this protocol: close them before upgrade. This ticket does not promise compatibility with old writers.

For recovery, keep browser storage. Download the current encrypted backup, or **Download pre-transition backup** after a committed transition. The latter contains the state before conversion, not later edits. Restore in a clean profile; an existing ID blocks restore. Version 1 recovery restores exact original encrypted records; the next collection load validates and transitions them again. Do not delete a source merely to bypass the ID check. See [backup operations and limits](password-manager-backup.md).

Retention costs space: source database, staged database, and embedded recovery backup can coexist. Failed staging can leave unlisted encrypted databases. There is no automatic cleanup or purge. Both current and retained pre-transition data can include deleted records and old passwords. Keep that in mind when retaining or distributing backups. The total backup limit remains 16 MiB / 10,000 current records, including embedded recovery bytes in the byte limit. Oversized transitions stop before publication.
