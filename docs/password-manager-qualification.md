## Fault model: injections are not physical failures

- Offline core operations use Playwright's actual offline mode and a stopped loopback server. Cache tests deliberately delete WASM or serve failed/mismatched deployment assets. This is not evidence of real browser eviction policy.
- Denied storage, startup quota and missing WebAssembly states override browser APIs. Clipboard denial rejects `writeText`. These prove application response, not actual user permission policy or disk exhaustion.
- Built import quota overrides `IDBObjectStore.put` for the SQL `records` store and throws `QuotaExceededError`. SQL/WASM, encryption, staging and the destination are real; the fault is injected. The test confirms the injection was reached, restores the API and checks the complete persisted destination.
- Public persistence suites use the same established browser API boundaries. Lost-write tests redirect persistence; uncertain tests reject a read after publication. They do not simulate a power cut or prove filesystem durability under hardware failure.
- Late-result tests gate existing public API promises around real persistence. Deadline tests change wall time and dispatch resume events. They are not actual operating-system suspend/lock tests.

## Safe operations

1. Load the production app online and wait for **Offline ready**. A first-ever visit without cached assets cannot start offline. Keep an external encrypted backup; browser storage is not a backup.
2. Before upgrade, close old application tabs. Old writers do not use the current Web Locks protocol. Keep the source and a verified external backup. Do not rewrite applied migrations or clear real data to bypass an incompatible development history.
3. For recovery, use **Download encrypted backup**, verify that the browser saved the file, then test **Restore encrypted backup** in a clean profile with the original master password. Check the full ID and contents. Existing IDs cannot be overwritten. See [backup operations](password-manager-backup.md).
4. Use **Download pre-transition backup** only for the retained old snapshot. It does not include later edits. Version-1 recovery transitions again when opened by the current app.
5. For migration, use only the [personal-json-v1 subset](password-manager-json.md). Preview all paths/counts before import. Unknown data blocks the whole batch. Cancel or explicitly import all duplicates as new; never infer overwrite rights from a name or external ID. See [import](password-manager-import.md) and [export](password-manager-export.md).
6. Plaintext JSON exposes credentials, history and private keys. Export requires explicit confirmation. Protect/remove the file as appropriate. It excludes Trash, local settings and provenance; it is not complete recovery.
7. After an unconfirmed write, lock, reopen and check authoritative items/full IDs before retrying. A sent write can commit after lock. Do not claim cancellation or delete a possibly published destination. Do not clear site data as a repair.
8. For missing assets, reconnect for a complete deployment. Cache-only repair must leave IndexedDB intact. See the [app delivery instructions](../apps/password-manager/README.md#readiness-updates-and-recovery).
