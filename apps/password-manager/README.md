# Password manager: collection-backed secrets

Sign in through the framework-independent `@of/sdk`, discover/create filesystem Storage Resources, and create, edit, or delete secrets using `@aicacia/storage-db-collection` plus the **official** `@tanstack/svelte-db` live-query binding. The legacy SecretStorage implementation and direct writes have been removed; only form state remains local. Explicit Refresh observes external changes and manually recovers a failed connection.

## Local setup

From the workspace root:

```sh
pnpm install --frozen-lockfile
pnpm --filter @aicacia/idp-client build:esm
pnpm --filter @aicacia/native-fetch build:esm
pnpm --filter @aicacia/oidc-client build:esm
pnpm --filter @aicacia/storage-client build:esm
pnpm --filter @of/sdk build
pnpm --filter @aicacia/storage-db-collection build
pnpm --filter @aicacia/svelte-headless prepack
```

Copy this app's `.env.example` to `.env` and configure `PUBLIC_URL`, `PUBLIC_IDP_BASE_URL`, and `PUBLIC_STORAGE_BASE_URL` for your running, provisioned Installation. Keep explicit service prefixes (for example `/idp` and `/storage`); Storage need not share the IdP host. `PUBLIC_LIDP_BASE_URL` is obsolete and is no longer read. The sign-in screen can select a different IdP service base; an explicitly selected base is retained by the existing `idp-api-url` preference. Configure Storage independently. Changing an environment default does not overwrite that preference. `PUBLIC_URL` must match the browser's actual origin/base, including the registered `${PUBLIC_URL}/callback` redirect URI. Use browser-trusted HTTPS/WSS certificates (and the Installation's allowed browser origins); never work around certificate or authorization errors by disabling security. The public configuration contains service locations, not credentials.

```sh
pnpm --filter password-manager dev
```

Use a provisioned Installation User permitted to onboard Applications. The frontend supplies logical Application ID (Application URI) `password-manager.aicacia.com`, never a configured OAuth Client ID. Initial authorization carries `application_id` and registration metadata without `client_id`; the authorization UI registers on Accept using the User's authentication, then uses the IdP-generated Client ID for consent and code issuance. The callback carries `code`, PKCE-bound `state`, `iss`, and the issued `client_id`. OIDC validates the callback and, after code exchange, authenticates `GET /oauth2/client/{client_id}` with the obtained access token to verify the returned Client ID and canonical Application URI before persisting the ID or tokens; reload, refresh, SDK identity, and Storage then use that ID. The existing client exchanges the current User's token at the selected IdP and uses a Storage-Audience Access Token. Socket opening requests both read and write authorization. Catalog discovery is not a resource-access grant.

## Behavior

- Select a Storage Resource by **Filesystem ID**, not its potentially duplicate name. Labels display both. Create filesystem opens the returned ID; on a fresh filesystem, the missing `secrets` directory is correctly empty.
- The collection eagerly validates one JSON file per secret at `secrets/<Secret ID>.json` using `SecretSchema`. Storage listing names are full paths. The editor preserves additional URIs, the first URI's match mode, custom fields, creation/deletion timestamps, unedited notes, and existing history. Clearing Website removes only the first URI. Changing Secret appends the previous secret and a change timestamp; other edits do not add history. Save validates required Name/Secret and updates `updatedAt`.
- Initial loading, empty, ready, malformed-record, and authorization failure are distinct. A failed or partially malformed load is never shown as an empty filesystem. Ordering is favorite-first, then name, through the live query, not a second array in component state.
- Selecting another filesystem destroys the old collection/query and clears editor selection. The same applies to an authenticated User/IdP change, route teardown, or Sign out. SDK retirement synchronously removes the browser and invokes existing adapter cleanup. Cross-tab synchronization is not implemented; another tab revalidates on its next authenticated operation or reload. Late responses cannot populate a replacement view. Keys deliberately remount the application view at these security/lifecycle boundaries.
- New secret, Save, and Delete use collection mutations. The list responds optimistically; controls are disabled while persistence and authoritative reload are pending. Success appears only after settlement. Reopen or reload to verify persistence. There is no separate secrets array or direct Storage write bypass.
- A rejected write rolls the list back to reconciled authoritative records and keeps form edits visible, with an error rather than a success notice. Review before retrying. An unacknowledged write can have persisted: after successful reconciliation the error remains visible and the save editor closes so it cannot blindly create a duplicate. Select the resulting record to inspect it.
- Disconnect, timeout, or failed reconciliation hides the list/editor and warns that a sent write may have persisted. **Refresh** and inspect the outcome before retrying. There are no automatic write retries or durable offline writes. The adapter bounds socket opening/token exchange and each Storage request to 30 seconds; a silent connection is closed and the mutation rejects as uncertain. This is a per-request deadline, not a whole-snapshot deadline. Switching/reopening cannot cancel a write already sent.
- Switching filesystem or authenticated context during a write clears old records and drafts; old completion/error notices cannot appear as the new context's result. A sent write may finish in the old filesystem.
- **Refresh** reloads additions, updates, and deletions on the existing collection, reusing a healthy socket and reopening a failed one only when requested. It is disabled during writes, and write/editor controls are disabled during refresh. A successful refresh closes unsaved form edits, so they cannot overwrite an external edit via a stale editor. A failed/partial/malformed refresh shows an error and hides old records instead of publishing incomplete/empty data. Correct the service/authorization/content problem and explicitly Refresh again.
- **Open filesystem** creates a fresh collection for the current selection, discarding its current form state. Selecting another Filesystem ID opens it automatically. There is no polling, automatic reconnect, or change subscription.
- Connections and decrypted records live in memory only. No browser secret persistence, IndexedDB, localStorage secret cache, or offline mutation outbox is added. The existing OAuth/session preferences are separate from secret storage.

The browser sees secret contents, and Storage receives their JSON representation; this adapter adds no client-side encryption. TLS protects transport only when correctly deployed. This example is not evidence of end-to-end encryption or a production-grade password vault. Do not use real passwords for qualification. Do not log tokens, WebSocket URLs containing access tokens, secret contents, or export unredacted browser network traces. Server-side Node replication does not make the browser snapshot live across clients. Sequential reads are not an atomic multi-record server snapshot. The adapter supports single-record mutations only and rejects batches before writing. It does not provide compare-and-swap or protect against another client's concurrent edits.

## SDK authentication and credential policy

`src/lib/common/state/sdk.ts` is the single browser auth composition point: environment/preferences and Application/OAuth Client metadata configure an immutable SDK instance. The app still owns safe return-to navigation, route guards, and notifications. Callback/restoration establishes identity using trusted OIDC userinfo, not token presence or decoded claims. The IdP listener base, canonical issuer, Application URI, and OAuth Client ID remain distinct. Configuration changes dispose the previous instance.

The SDK explicitly uses OIDC **localStorage** persistence for access/refresh tokens and state-bound PKCE transactions, preserving full-page redirects and reloads. Memory-only state cannot continue a full-page redirect. Cache namespaces are derived from immutable IdP base, optional preprovisioned OAuth Client ID, callback URI, and registration/Application metadata. The IdP-issued Client ID is persisted within that namespace, rather than changing it after onboarding. Other clients cannot consume those credentials or pending transactions. Legacy authority-only caches are ignored (no migration); sign in again. Remove legacy plaintext entries manually through browser site-data controls. Browser storage must be enabled. Credentials remain readable by same-origin JavaScript, extensions, and local inspection; XSS compromises them. This is not encrypted credential storage; decrypted secrets are never persisted there.

The app's Sign out is **local-only**: invalidate captured Storage capabilities and guarded requests and synchronously destroy the collection/query/socket/editor before navigation, with no provider availability requirement. Local deletion is neither provider logout nor token revocation. The SDK separately supports optional provider logout and reports failure without restoring local authentication. Same-identity renewal retains collections. Changed identity/missing credentials/terminal authentication failures retire the context; connectivity errors and resource denials do not indiscriminately sign out. Late discovery/callback/renewal results cannot revive a disposed instance.

`Browser.svelte` obtains `getSdk().storage()` after authentication and passes that captured capability directly to `Filesystem.svelte` and the existing collection adapter. The transitional app Storage factory and raw bearer-token wiring are deleted. The SDK never depends on the adapter or Secret schema, and the adapter never depends on the SDK. SDK `openSocket()` resolution is the one-owner handoff: the SDK/Storage client cleans failed, canceled, or obsolete attempts; the adapter cleans successfully adopted guarded connections through its existing disposal. The app's synchronous session subscriber unmounts collections/queries and clears editor selection on context retirement. Filesystem-only switching leaves authentication intact. Retained capabilities reject obsolete discovery/create/open results and retained connection requests cannot send new or queued work after retirement. The event-only transport surface does not expose raw send or token-bearing socket URLs. Already-sent writes can persist, so sign-out or switching is not remote cancellation. See [SDK workflow/security documentation](../../packages/sdk/README.md).
