# Node API contracts

These are current owner/host contracts, not a claim of complete offline-first or platform acceptance. [System design](design.md) defines requirements; [operations](operations.md#qualification-boundary) preserves historical bounded Ubuntu qualification and deferred GUI/deployment limits. This documentation update independently runs no code tests or native installation; [operations](operations.md#qualification-boundary) records the supplied focused validation results and their limits.

## Owner contracts

IdP owns identity administration, OAuth/OIDC, Device membership and public signer trust. Management owns permissions, restrictions, selections and replication admission. Storage owns namespace catalogs/resources and local Residency. Identity administration goes directly to IdP, never through a Management proxy.

The paths below are owner-relative; unified hosting mounts `/idp`, `/management` and `/storage` once. They are not a substitute for complete live OpenAPI documents.

| Owner      | Current contract                                                         | Authorization boundary                                                                                                                                                      |
| ---------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IdP        | User, Application, Client and Device administration                      | Verified User actor; exact action and Application/Installation target                                                                                                       |
| IdP        | `GET /devices/identities/{device_id}`                                    | Ordinary authenticated service caller with `idp.device.lookup`; current signer-backed Device/owner binding                                                                  |
| IdP        | `PUT /devices/{device_id}/owner`                                         | Exact Installation `idp.devices.transfer`; active new User; acknowledgement is not cleanup completion                                                                       |
| IdP        | `POST /replica-signers`, `PUT`/`DELETE /replica-signers/{member_id}`     | Exact Installation `idp.replica_signers.enroll`, `.rotate`, `.revoke`; public approval never supplies private capability                                                    |
| Management | `POST /permissions/evaluate`                                             | Same verified User actor, or separately registered IdP evaluator Client with only `management.permission.evaluate`; `idp-management` audience and exact typed action/target |
| Management | Device selection, resource-specific deselection, restriction read/update | Distinct permissions plus current local IdP Device identity; ownership and administrator restriction grants are separate                                                    |
| Storage    | Database/filesystem catalog CRUD and filesystem Residency                | User subject/Application namespace, kind audience and typed read/write action; current local owner/policy/cleanup gates                                                     |

`/replica-signers` and its permission identifiers are current exact-permission contracts despite their historical spelling. They do not designate privileged replica Nodes and must not be removed merely by searching for `replica`. Storage/Management request bodies, statuses, cleanup and Passthrough limits are documented in [Storage API](../crates/storage-service/docs/api.md). OAuth password authentication remains a supported sign-in grant; it is not a Node-join mechanism.

`GET /replication/devices/{endpoint_id}/selections` on Management requires a Client token with the configured Storage audience and `management.replication.read`. Its response now requires `deviceId`, `endpointId`, `ownerSubject`, `adminAllowed` and `resources`. A successful read attests the current approved signer-backed Device and active owner; it does not authorize caching that approval. Missing trust, missing policy, mismatched ownership or pending transfer cleanup denies. `adminAllowed: false` is a current restriction, not a provisioning failure or permission grant.

Independent Storage uses these fresh responses for its existing operation/frame/response authorization when no local policy owner is injected. A local denial never falls back to the remote service. Only service tokens are cached, not policy decisions. Cancellation and local-copy retirement are rechecked after asynchronous policy evaluation before a queued frame can be released. Remote transfer cleanup acknowledgement is not implemented: pending cleanup and retired local roots remain denied rather than automatically reactivated. These bindings do not establish independent Create/Join. Old responses containing only `resources` fail closed in the updated Rust consumer; regenerate consumers from the complete owner document when deploying this contract.

## Prefixes and application identity

Unified runtime assigns the three service prefixes. Owner OpenAPI routers normalize prefixed paths for owner-relative generation. Configure clients with the verified service base, append an owner-relative path once, and inspect the complete specification rather than assuming its server/path convention. Do not turn `/idp/idp`, `/management/management` or `/storage/storage` into compatibility routes.

An independently configured IdP may use `management_permissions` with an HTTPS Management service base and its separately established evaluator Client. It issues the exact-scope service token locally and validates the echoed decision and audit identity; transport, authentication or policy failure denies without database fallback. Local/unified permissions take precedence and require no remote evaluator. This client does not establish the relationship or complete independent setup. See [qualification](../.scratch/ui-driven-node-bootstrap/evidence/14-independent-permission-evaluation.md).

Management's built-in Application URI/audience `idp-management` is not the `/management` transport prefix. Keep Canonical Issuer, token audiences, public Application URIs, listener addresses and authenticated endpoint identity distinct. Ordinary local service clients retain their separate scopes/audiences and secure secret references in [operations](operations.md#secrets-and-local-identity).

## Setup, join and readiness

`/setup/bootstrap` and its unused HTTP setup/join request contracts were removed through the source owner workflow. There is no replacement unauthenticated HTTP setup mutation, password-grant join, Storage-only join or privileged replica mode. Native IPC and explicit CLI create/join remain existing entry points. API-driven web setup is in progress with a separate host-generated initial admission code, not a public administration shortcut.

The native setup-only router exposes `GET /lidp/setup/status` with the Installation stage. This is a setup probe, not a durable public-readiness API. `SetupStage`/`SetupStatus` remain legitimate active contracts; do not delete them with obsolete bootstrap models. Native commands coordinate explicit create/join, offer approval, retry, Device completion and local reset. Join pins a trusted reachable approving endpoint and binds Installation, Device/member and independent public signer. A persisted approval receipt alone does not authorize ordinary DATA or complete public bootstrap.

`UnifiedRuntime::node_public_ready` / `node_join_public_ready` check current owner trust and signing capability. Desktop additionally retains Installation/Device completion state and evaluates current runtime readiness. A running HTTPS listener, setup status, endpoint allowlisting, completion marker, successful sign-in or Residency acknowledgement alone is not complete readiness. Partial setup remains incomplete; completed Nodes are required to remain usable after offline restart without a freshness lease.

Fresh ordinary unified startup now serves restricted setup status/admission over verified HTTPS. `GET /idp/setup/status` initially reports `stage`, `state`, `ready:false` and explicit `owners:["idp","management","storage"]`; unavailable admission reports 503 with the same scope. `POST /idp/setup/admission` verifies one `Authorization: Setup <64 lowercase hex>` header and returns 204, without granting membership, creating an administrator or completing setup. Wrong/missing codes deny; browser Origin must exactly match the configured HTTPS `idp.ui_public_uri`. There are no cookies or credentialed CORS. Codes are retrieved through protected host management, never public status, URLs or logs.

Independent IdP, Management and Storage fresh startup now exposes owner-relative `GET /setup/status` and `POST /setup/admission` on actual verified HTTPS, with singleton `owners` scope. Configured composition applies its prefix once. The same app uses explicit IdP/Management/Storage service bases, discovers one unified code target or three singleton targets, and sends a selected code only to its exact validated base; sharing an origin does not share admission. Web status/loader/render tests and native branches are execution-qualified, not actual GUI certification.

This slice is **not complete web Create/Join**. Unified `POST /idp/setup/create` requires the setup code and returns `202 Accepted` after durable exact intent binding, without waiting for owner initialization. Accepted work belongs to the host and survives submitting-client disconnect. Observe completion through `GET /idp/setup/status`; only ready status includes the public login Client. Retained Create/Join startup reports `creating`/`joining` while owner reopening is in progress, then verified `ready`, actual `unfinished`, or `unavailable`; an in-progress reopen is not stopped setup or readiness. `POST /idp/setup/cancel` requires code authorization and the exact active nonsecret intent; no active or mismatching operation returns 409, while 204 means cancellation was signaled, not that cleanup has finished. Exact completed Create retries use ordinary password authentication and return 200; retired setup codes authorize no new work. The focused unified HTTPS regression now covers completion, authentication, retry/retirement and offline reopen. The app now submits unified Create through HTTPS, observes host status, preserves exact in-memory retries after uncertain responses, and sends explicit code-authorized cancellation. Web sign-in discovers the verified public login Client instead of hard-coding `idp-web`. Setup codes/passwords are transient; closing the page does not cancel accepted work. After reload, `POST /idp/setup/intent` with the current host code recovers the exact nonsecret Create intent (200), or reports no bound intent (204); missing/invalid/retired codes deny, and malformed protected tuples return 503 without repair. The app verifies current status/scope before adopting that intent and requires newly entered code/password for an exact retry. Completion of owner provisioning without durable code retirement stays unfinished on reopen; an authorized exact retry can finalize retirement without replacing identities. See [recovery evidence](../.scratch/ui-driven-node-bootstrap/evidence/11-create-recovery-finalization.md). Unified `POST /idp/setup/join` accepts only an operation nonce, Node name and canonical pinned peer; authenticated issuer discovery precedes durable admission and `202`. The app has unified Join, exact-intent recovery/cancellation and source User-authorized approval controls. The focused production HTTPS lifecycle now qualifies unified Join completion, authenticated Storage use, source-offline reopen, interruption/rejection/exact retry and complete-but-unretired finalization under unchanged bounds. This is API-seam evidence, not a rendered GUI or complete independent-owner deployment claim. Independent Create and Join workers now implement the API-only contracts below; app mutation wiring, generated independent setup clients and remaining lifecycle cleanup remain unfinished. Do not advertise complete web setup. See [current Join qualification](../.scratch/ui-driven-node-bootstrap/evidence/27-direct-storage-and-join-completion.md) and [web controls](../.scratch/ui-driven-node-bootstrap/evidence/15-web-join.md). See [backend evidence](../.scratch/ui-driven-node-bootstrap/evidence/08-host-owned-create.md) and [app/OpenAPI evidence](../.scratch/ui-driven-node-bootstrap/evidence/09-unified-web-create.md). Code verification alone does not provision a Node. Existing active CLI Create/Join metadata is not reinterpreted as fresh. A neutral awaiting-choice host deliberately rejects CLI Create/Join until purpose selection is safely wired; do not reset it to bypass this partial state.

The CLI retains explicit no-config `unified-server create` and `join` for fresh or matching retained active intents, and existing-Node serving. Internal IDs, secrets, audiences and roots are derived/retained; hidden administrator password entry is the create default and `--password-file` is optional automation. Both create and join require OS CA installation and native-root production HTTPS verification. A new Installation retains a unique logical issuer unrelated to its API address; join authenticates purpose/nonce-bound issuer discovery against the pinned peer before producing Node material. `--config` remains optional. See [bootstrap operations](operations.md#automatic-unified-cli-bootstrap).

### Independent Create worker contract

Each owner exposes owner-relative `POST /setup/create`, `POST /setup/intent` (nonsecret recovery), and `POST /setup/cancel` on its existing verified HTTPS listener. Each mutation/recovery requires that owner's own `Authorization: Setup <code>` capability and the configured browser Origin when present. A code admitted by another owner is not authority here.

Create submits the same exact nonsecret tuple to all three owners: `purpose:"create"`, a 32-character lowercase-hex `operation_nonce`, `administrator`, `node`, canonical distinct HTTPS `idp`/`management`/`storage` bases, `issuer` equal to the selected IdP base, and `peer:null`. Only the IdP request includes the transient `password`. After durable exact binding, each owner returns 202; work belongs to the host, not the submitting connection. Observe `GET /setup/status` (`awaiting_choice`, `creating`, `unfinished`, `ready`). Cancellation returns 204 when signaled, not when cleanup finishes. Exact active retries return 202; conflicting tuples return 409. Recovery returns the retained tuple or 204 if none, never a password/code/secret. Retired codes deny all further setup mutations and recovery. Completed-but-unretired restart remains unfinished until an authorized exact finalization.

`GET /setup/independent/public` publishes the operation-bound public Client registrations and owner facts, including the public login Client at `facts.login_client` on IdP. This metadata is not setup authorization. Worker-only initiation delivers a one-use challenge to the exact recipient's `/setup/independent/challenge`; the recipient sends its protected secret directly to its bound IdP's `/setup/independent/register` over verified HTTPS. Neither route returns credentials or challenges. Registration requires an outstanding exact capability, not merely the public operation nonce; substitutions and replay deny. Redirects are disabled. These worker contracts are not yet generated app SDK routes; independent app mutation wiring and client generation remain separate work.

The workers reuse owner-local handles for seed and serving, retain one actual Management Device/endpoint, and create no Storage resources or per-process Nodes/Devices. Stopped reopen uses retained local keys/records without peer import or reseeding. The [Create worker receipt](../.scratch/ui-driven-node-bootstrap/evidence/independent-create-worker.md) distinguishes HTTPS lifecycle qualification from focused challenge-handler tests and deferred deployment/app work.

### Independent Join worker contract

Each owner accepts `POST /setup/join` with its own `Authorization: Setup <code>` and the same tuple:

```json
{
  "purpose": "join",
  "operation_nonce": "0123456789abcdef0123456789abcdef",
  "administrator": "",
  "node": "Joining Node",
  "idp": "https://target.example/idp",
  "management": "https://target.example/management",
  "storage": "https://target.example/storage",
  "issuer": "",
  "peer": "https://source.example/management#<canonical-pinned-endpoint-id>"
}
```

`peer` is the source's exact HTTPS **Management base**, including its configured prefix, followed by `#` and the independently verified canonical endpoint fingerprint. It is not the unified bare-endpoint choice. Each target owner authenticates signed purpose/nonce-bound discovery before initial durable admission and returns 202. Empty `issuer` is resolved to the source Canonical Issuer; a supplied conflicting issuer denies. Join rejects any `password` and requires empty `administrator`; no administrator or password verifier is seeded/imported.

Recovery is `POST /setup/intent` with that owner's code and no body: 200 returns exactly the bound tuple above with its authenticated nonempty `issuer`; 204 means no bound operation. Recovery neither resumes work nor returns credentials. Retry the recovered tuple via `/setup/join`; an empty issuer on a retained retry reuses the retained issuer without rediscovery, allowing source-offline completed finalization. Purpose, nonce, names, bases, peer and nonempty issuer conflicts deny. `/setup/cancel` takes the recovered exact tuple, returning 204 when cancellation is signaled, or 409 for no matching active operation. Retired codes return 401 for mutation/recovery.

All independent status responses use `{"stage":"installation","state":"joining","ready":false,"owners":["management"]}` with the actual singleton owner. States are `awaiting_choice`, `creating`, `joining`, `unfinished`, or `ready`; only `ready` sets `ready:true`. Invalid admission returns 503, not fresh permission. Status contains no peer approval offer, login Client, password or secret; public login discovery remains `/setup/independent/public` at IdP. Poll every intended owner: one ready owner is not global completion.

On the existing source Management base, ordinary authorized User bearer routes are `GET`/`PUT /node-joins/acceptance` (`PUT {"accepting":true}` returns 204), `GET /node-joins/pending`, and `POST /node-joins/{offer_id}/approve` or `/reject`. Pending entries include `offer_id`, `authenticated_endpoint`, and the exact public `request`; Device ID, signer member/key IDs, endpoint and target bases remain distinct bindings. Approval returns 202 for host-owned work; rejection returns 204. Missing/unauthorized User evidence denies with 403. Target Setup codes do not authorize source approval. Approved owner-local public history imports are distinct from resource synchronization and exclude private credentials. Stopped completed reopen uses retained local state, without source contact or reseeding.

A durable `initialized.json` fence precedes the first worker record/provider attempt. Lost initialized worker evidence refuses even before a domain store exists; operators must not delete setup files to force retries. Recipient callbacks perform provider/network work outside the privileged lifecycle gate and revalidate the exact active operation before recording progress. Configured-origin CORS covers the complete setup/normal router composition; normal OAuth/Bearer authentication is unchanged. See the [Join/security qualification receipt](../.scratch/ui-driven-node-bootstrap/evidence/independent-join-security.md). Existing-app wiring and generated independent clients remain with the integration owner; these Rust contracts are not generated SDK claims.

### Public operator-login Client

CLI create **and** join automatically provision a retained public operator-login Client, verified on completed retry/reopen. CLI output supplies the actual Client ID, allowed login scopes and token-exchange audiences; `serve` also supplies the API/token endpoint addresses. No manual Client registration or secret is required. Bundled owners require no confidential service relationship Clients. The public login Client has token endpoint authentication `none`, password/refresh/token-exchange grants, and login scopes `openid`, `profile`, `email`.

Use ordinary `POST /idp/oauth2/token` with an `application/x-www-form-urlencoded` body: `grant_type=password`, the actual printed `client_id`, existing User `username` and securely handled `password`, and an allowed `scope` such as `openid`. Do not put the password in argv/logs or supply a confidential-client secret/Basic header. Ordinary token exchange selects the required permitted audience/action scopes before using the resulting User bearer for approval routes. The audience allowlist does not confer User permission; password sign-in is not Node join. See [login operations](operations.md#public-operator-login).

### Production Node-join approval routes

These routes are already fully prefixed in the composed HTTPS router; append them to the Node origin, not to an already `/idp`-suffixed base:

| Method/path                         | Request/response contract                                                                |
| ----------------------------------- | ---------------------------------------------------------------------------------------- |
| `GET /idp/node-joins/acceptance`    | Returns `{"accepting": true/false}`                                                      |
| `PUT /idp/node-joins/acceptance`    | Accepts/returns `{"accepting": true/false}`                                              |
| `GET /idp/node-joins/pending`       | Returns an array of `offer_id`, `authenticated_endpoint` and validated `request` objects |
| `POST /idp/node-joins/{id}/approve` | Approves the exact pending offer ID; returns `NodeJoinApproval`                          |
| `POST /idp/node-joins/{id}/reject`  | Rejects the exact pending offer ID; returns `204 No Content`                             |

Every route requires `Authorization: Bearer …` and existing IdP `authorize_node_join_approver` checks. Missing bearer returns `401`; permission denial `403`, missing offer `404`, invalid/conflicting state `409`, and other owner failures `503`. There is no unauthenticated enrollment, API-key/password approval shortcut or requirement to call repositories. Issuer probes are handled by the serving background task while acceptance and public readiness permit; they do not require a pending-list request and do not enroll the caller.

Approval commits and verifies the exact IdP Device/member/signer/owner binding before initializing an absent empty Management policy. It preserves existing policy, refreshes transport admission and rechecks authorization/enrollment before the signed reply. Failure after enrollment remains partial for exact retry; rejected enrollment creates no policy. Transport approval grants no resource selection/access.

Desktop retains corresponding runtime/native commands. Fresh create automatically retains a unique logical issuer; native join takes the pinned peer and Node name, discovers the issuer through the shared authenticated discovery helper and reuses retained intent on retry. Manual issuer UI/input is removed; this is not a new GUI acceptance claim. Historical native authenticated completion/reopen is qualified only within the bounded Ubuntu scope. **Verified GUI approval, profile-B completion and two-profile GUI offline restart remain deferred and not observed.** Offer display must not be promoted to approval or full-spec acceptance.

## Generated clients

Generate from complete specifications obtained from verified current owner endpoints using the existing temporary-output workflow in `scripts/generate-openapi-client.mjs`. The historical owner-generated inventory contained 88 operations across nine groups (IdP 50, Management 24, Storage 14), including permission, Device, restriction, selection, transfer and Residency operations. That count is not a current live inventory or evidence that the composed Node-join routes are included in owner OpenAPI/generated clients. Consume the actual host routes above; do not invent HTTP setup/readiness operations from native methods.

The unified setup document has its own generated `@aicacia/idp-client/setup` subpath. Run `OPENAPI_SPEC_URL=https://node.example/idp/setup/openapi.json pnpm run openapi:setup` from the IdP client package, then `pnpm run build:esm`. The existing generator requires all six declared setup operations, including Join (whose runtime acceptance remains blocked), and publishes only `src/setup`; normal IdP regeneration preserves that subtree and still requires its full normal owner inventory. Run generation serially. This setup SDK takes a verified HTTPS **host origin**, since its paths already include `/idp`; it is not the owner-relative base convention above. The app consumes its generated request serializers through the checked HTTPS setup helper. No independent-owner Create/Join routes are implied. See [generation evidence](../.scratch/ui-driven-node-bootstrap/evidence/12-setup-generation.md).

Missing URLs, unreachable endpoints, incomplete operations/supporting files, generator failure or staged formatting failure must leave checked-in generated sources unchanged. Never hand-edit generated models/routes or use stale generated setup APIs as evidence that a removed route is supported. Historical generation at `dcdf8e9` removed `SuperRoutesSetupApi`/`SetupBootstrapRequest`; the new separately generated setup subpath does not restore those obsolete routes.

## Storage client consumption

The caller delivery uses explicit `idpBaseUrl` and `storageBaseUrl`, not legacy `baseUrl`/`audience` options or an origin-derived audience fallback. Password-manager requires both `PUBLIC_LIDP_BASE_URL` and **`PUBLIC_STORAGE_BASE_URL`** as complete service bases, including `/idp` and `/storage`; `PUBLIC_STORAGE_AUDIENCE` is no longer consumed. Token exchange selects `resource=storage:filesystems`; catalog calls append `/filesystems` to the Storage base and the socket uses that base with flat Storage requests, preserving each prefix once.

Public Storage package exports resolve through `esm`/`types`. Explicitly run the package's normal build before publication; there is no automatic `prepack` hook. Distribute the complete output, including compiled generated dependencies, not only the five tracked output files. Workspace source consumption and distribution builds are separate; see [operations](operations.md#client-configuration-and-distribution).
