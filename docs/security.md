# Node security boundaries

[System design](design.md) states the equal offline-first requirements. This source audit records current boundaries without claiming full host/platform acceptance. Detailed contracts live in [IdP local security](../crates/idp-service/docs/local-security.md), [Storage security](../crates/storage-service/docs/security.md) and [public persistence](public-persistence.md).

## Identity is not interchangeable

A token subject identifies a User or Client Principal. A Node Signer identifies its issuer. An authenticated Iroh endpoint identifies the connection peer. None may substitute for another, and an endpoint ID or message-source claim is not a User actor or resource permission.

IdP administration uses validated bearer identity with exact audience, action and target. Management permission evaluation binds a User caller to the same requested User; only the separately registered least-privilege evaluator Client may assert a User under its explicit evaluator scope/audience. Alternate actor/subject headers grant no authority. Existing `x-actor-subject` impersonation-denial tests are intentional negative evidence, not obsolete authentication features. Selection supplies a kind-specific Storage token in the typed `storageAccessToken` body field, not an `X-Storage-Authorization` override.

`/replica-signers` is the current authorized public Node-signer API. Its historical name, `DbReplicaSignerRepo`, persisted membership table names, `replica` persistence features and CRDT source/receiver roles do not create a designated authority/privileged replica topology. Public signer approval is not private signing capability or blanket synchronization permission.

Storage transport bases are not token audiences. The password-manager caller delivery exchanges the current User token for `resource=storage:filesystems`, with exact typed Storage actions: read for listing, write for creation, read/write for the editable filesystem socket. Explicit IdP/Storage service bases replace the audience/origin fallback; no actor override or wider permission is introduced. Historical caller/package checks do not qualify server authorization, GUI approval or current deployment acceptance.

## Local trust and learned denial

Each Node checks persistent locally trusted IdP/Management owner state. Optional independent IdP permission evaluation uses the established distinct evaluator Client over native-trust HTTPS, verifies the exact echoed request/audit identity and fails closed on remote failure. It never falls back to reading a remotely deployed Management database. Unified/local evaluation remains authoritative when present, including local denial, with no remote dependency or fallback. Unified service relationships use the local contexts; unavailable or invalid local evidence denies. Loss of a remote peer alone is not authorization loss, and there is no 30-second trust freshness gate. Normal token expiry/renewal margins, purpose-specific pairing controls and bounded test waits are not trust leases.

Connection admission and approved endpoint allowlisting are not resource authorization. Pairing is purpose-bound approval exchange, not general access. Security-history exchange checks exact local context-sync permissions, authenticated membership and public-history integrity. Resource protocols independently check ownership, namespace, selection and restriction at actual apply/read/write boundaries, including existing connections. Learned denial blocks subsequent work; already-authorized work may finish. Partitioned Nodes may temporarily diverge, and OAuth consumption is atomic locally rather than globally single-use.

## Credentials and persistence

Keep independent private signers, raw passwords, raw secrets and confidential-client authentication material local in supported secure storage. Only reviewed public/domain projections and validated scoped history may synchronize. Removed mixed-row credential fields are rejected by current schema checks; externally dropping columns does not sanitize historical CRDT disclosure. Do not delete active local-only credential repositories, secret references, credentials metadata, or rejection fixtures merely because they mention a removed field.

`of` depends on public `ofdb-sql` and `ofdb-kv` facades. Owner-internal transitive dependencies, facade backend feature names and `.redb` data-file extensions are legitimate, not direct internal persistence dependencies. `offs` owns filesystem persistence, `ofnet` owns reusable endpoint/mesh/pairing/routing, and `of` owns domain authorization and protocol adapters. Preserve separate context roots and ordinary least-privilege local service-client scopes/audiences; no compatibility wrappers or central-role fallback are required.

## Initial web setup admission — partial implementation

The same app can run on web without Tauri; initial HTTPS setup is authorized by a host-generated 256-bit code retrieved through protected host management. The dedicated Unix state is owner-only and nonsymlink, guarded by an exclusive process-lifetime lock; it is not public host metadata or a replacement for secure-provider-backed domain keys. Exact code comparison is constant-time, duplicate/malformed authorization denies, and errors/Debug do not disclose credentials. Binding and retirement are durable; invalid state or ambiguous IO fails closed without repair. No code enters HTTP status, URLs, logs or ordinary stdout.

Use `Authorization: Setup <64 lowercase hex>` only on setup routes, not as an ordinary OAuth token. Browser requests require the exact configured HTTPS UI Origin; no-Origin native clients still require the code. Explicit headers/noncredentialed CORS do not constitute identity or replace code authorization. Admission checks alone do not authorize later work: unified Create/Join bind validated exact nonsecret operation identity, coordinate mutation, preserve retries and retire the code only after owner verification. Cancellation and retirement have one serialized winner; once finalization wins, cancellation cannot return success. Current ready status rechecks local owner readiness rather than trusting the completion marker. Source Join approval still needs ordinary authorized User evidence.

Current implementation qualifies shared admission and neutral unified/independent-owner HTTPS startup, status/code verification, and focused native/web client/loader/render integration. Explicit `owners` scope comes from checked host metadata; it describes code scope, not membership or resource authority. The browser uses one unified target or separately validated singleton owner targets, never inferring shared authority from matching origins. Unified web Create is qualified by focused HTTPS completion/reopen tests. Unified API/app Join is implemented but its bounded runtime qualification still times out before readiness after source approval. SQL owner changes get the latest consumer run past its former overflow while preserving full history/conflict validation; neither contract tests nor UI controls establish successful Join. Independent-owner provisioning and cross-owner completion remain unimplemented.

Installer subprocesses are cancellation-owned and reaped, with host/admission leases held through ordinary process-group cleanup. Test verifier overrides are gated behind nondefault `api/test-support`; production requires installation and the native-root client. Cancellation fixtures do not certify escaped/new-session or privileged descendants, OS-denied termination or actual elevation. Normal protected API authentication and authorization are unchanged. A browser cannot install OS trust: desktop coordinates native consent, while web deployment must arrange required installation. No privileged installation was executed as a test.

## Automatic bootstrap and trust installation

Ordinary CLI `create`/`join` derives internal IDs, context roots, audiences and public settings. Bundled Management and Storage bearer validation and identity lookup call the current local IdP owner directly, retaining principal, signer/root, registration, Application and exact consumer authorization checks without confidential relationship registrations or service secrets. Bundled IdP→Management permission evaluation and Storage→Management replication authorization likewise use current local owner interfaces. Independent deployments retain authenticated HTTPS evaluator/client APIs and least-privilege credentials. Durable consumed attempt history and exact readback still protect Node signers, endpoint identity and TLS; missing attempted material never authorizes replacement. Hidden initial password entry is the create default; an operator-only nonsymlink password file is optional automation. Passwords never enter argv/config/raw-secret manifests. Explicit custom configuration is optional, not an internal-ID/secret prerequisite.

Create and join also automatically retain a separate public operator-login Client. Its printed ID/scopes/audiences are public metadata, not secrets or authority. Ordinary password authentication and token exchange still require valid User credentials, exact audience/action and current local permissions; no confidential Client secret or bootstrap-only sign-in bypass is introduced. Never put the User password in argv/logs or confuse this public Client with independent deployments’ confidential service relationships. Old one-/two-/four-slot bundled references and intents are refused unchanged; native explicit reset retains every historical Client/key-name reference through cleanup failure. No migration or secret regeneration is performed.

A fresh Installation retains a unique logical Canonical Issuer independent of its localhost API address. No-config join learns that issuer over authenticated pairing bound to purpose, fresh nonce and the operator-pinned endpoint before Node production. A fingerprint must be verified through a trusted channel; unsigned metadata and arbitrary discovered peers are not trust evidence. Retained identity/ports are not silently regenerated or migrated. Old bundled one-, two- and four-relationship records deny ordinary setup/reopen unchanged. Explicit native reset alone accepts their exact captured Client/credential references, preserving attempted-secret evidence and owner metadata across cleanup failure; removed relationships never receive fresh production authorization.

Source acceptance, pending offers, approval and rejection use the production `/idp/node-joins` routes with ordinary bearer sessions and existing IdP approver permissions. Acceptance/discovery is not enrollment. Exact IdP Device/member/signer enrollment and owner verification precede absent default Management policy initialization; existing restrictions/selections remain intact. Admission refresh and final IdP authorization/enrollment recheck precede the signed reply. Invalid enrollment cannot create policy. A post-enrollment policy/reply failure remains partial for exact retry, not authority rollback or replacement. Handshake retries do not add a general allowlist bypass or resource grant. See [API contracts](api.md#production-node-join-approval-routes).

Both CLI create and join (including continuation) require OS CA installation and protected retained localhost CA/server material. Denied elevation/trust, unavailable provider/tools or native-root verification failure stops setup. There is no skip-install, plaintext, browser-only or insecure-certificate fallback. Completion requires the production HTTPS router, current readiness, all context health routes, exact-scope Client tokens, ordinary authenticated owner calls, background startup and closure before publication. Verification disables redirects/proxies and uses native roots only. Completed-Node `serve` opens retained state and cannot turn incomplete/missing trust into freshness. The separate neutral startup path only accepts positively fresh roots or exact retained neutral prerequisites; it does not repair damaged active Node state.

Installing the local CA is an OS trust change, not merely a browser preference. Protect its private key and server keys as local sensitive material. Linux's matched platform anchor copy/refresh requires working elevation; macOS's login-keychain path is implemented but not newly qualified here. The CLI refuses unsupported platforms and non-localhost TLS addresses before material production. Desktop's existing native certificate preparation also requires OS trust installation/native-root verification; stale success markers do not waive that requirement. Desktop fresh create now automatically retains its own unique logical issuer and join uses the shared authenticated discovery helper against the pinned peer; manual issuer UI/input is removed. Existing retained intent is not silently replaced, and discovery does not change reset/recovery behavior.

## Qualification limits

[Operations](operations.md#qualification-boundary) preserves the historical bounded Ubuntu Linux x86_64 qualification, including native authenticated join/completion/offline reopen and narrower lifecycle/rotation/recovery results. **Verified GUI approval, profile-B completion and two-profile GUI offline restart remain deferred and not observed.** Real OS-provider persistence/loss recovery, native CA installation across platforms, containers, unattended deployment and broader process/crash behavior remain separately qualified concerns.

This documentation update independently ran no Cargo/GUI/live-endpoint tests and performed no native OS trust installation. [Operations](operations.md#qualification-boundary) records the supplied focused unit, production HTTPS, Desktop localhost and `ofnet` passes, plus blocked/failing frontend checks. Injected install commands and isolated native CA-file roots in the HTTPS harness do not modify or qualify a real OS trust store. No GUI acceptance is inferred. Focused/historical tests, receipts, generated routes and listener probes cannot waive current trust or qualification limits.
