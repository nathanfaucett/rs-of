# UI-driven Node bootstrap and unprovisioned API startup

Status: resolved

**Authoritative ownership correction:** Management owns Devices and endpoint IDs, their User ownership, approval/enrollment, transfer and revocation, restrictions and selections. IdP owns Users, credentials, Applications, OAuth Clients and token-signing trust—not Device/endpoint authority. Storage owns resources and consumes Management's current endpoint authorization. This supersedes contrary ownership statements and the pending multi-endpoint Node proposal in earlier revisions/receipts. The correction is required implementation work, not a request for another domain decision or a claim that the current code already conforms.

## Problem Statement

The original failure was that fresh unified startup refused with `no retained credentials; explicitly create or join first`, preventing app-driven Installation Setup. Neutral startup and parts of API/app Create/Join now exist, but the complete deployment flow remains unfinished.

Implementation has also accumulated excessive setup coordination, repeated schema/store initialization and verification, and confusion between fresh Installation creation and importing an existing Installation. A fresh Installation has no application resources to synchronize. Its work should be schema initialization, a small explicit identity/policy seed, protected local keys and the service bindings actually needed by the deployment—not three independent domain-bootstrap ceremonies. Device/endpoint authority has also leaked into IdP and been coupled to token-signer membership. That is an owner-boundary defect to remove, not a reason to invent a multi-endpoint Node enrollment model.

This reverses the intended experience: the operator starts the server and uses the app to Create a new Installation or Join another Node. The operator must not first run terminal provisioning commands or assemble internal configuration. The unified API does not serve the UI; the app owns UI presentation and interaction.

The same app runs bundled with services on desktop or as a web deployment without Tauri, using only APIs. Web deployments may expose each owner API independently or compose them through the unified API. Existing native-only setup contracts must change to support these deployments; removing the startup prerequisite must not permit unauthorized initialization or silently create an Installation.

## Solution

Allow the APIs to start without a completed Node and expose authorized setup/status contracts over HTTPS. The existing app presents Create or Join and drives those operations through APIs in its web deployment, without Tauri or a private parent-child control channel. Desktop bundles the same app and services, reusing the same setup behavior; native integration handles only capabilities that require it. Independent owner APIs and unified composition must both support the flow while preserving owner-local state and authorization.

Both Create and Join require OS-level CA trust installation and verified HTTPS. Desktop can coordinate native installation with explicit elevation/consent. A web browser cannot install OS trust: required installation is handled by the deployment environment on the relevant hosts/clients, not by a Tauri dependency or browser certificate-warning bypass. Preserve secure-provider protection and explicit failure; application/browser-only trust is not a substitute.

Keep the lifecycle small: open each required owner store and initialize its schema once for that runtime; Create seeds only the required identity and policy; Storage starts with an empty resource catalog. Reuse those open owner handles for provisioning and serving. Join is a distinct operation that obtains existing approved public identity/policy state needed for offline operation; do not put that synchronization path on fresh Create.

Setup establishes the persistent identity, policy, signing capability and service relationships needed for valid authenticated operations without a separate serving command. Normal protected APIs always require their existing authentication and exact authorization; there is no new switch that enables authentication after setup. Readiness checks must protect concrete incomplete-state invariants, not duplicate authentication or create a blanket availability gate. Restart reopens the retained Node without live peer contact. Partial setup remains incomplete, retryable under the retained intent, and explicitly resettable; invalid retained state is not treated as fresh.

## User Stories

1. As an operator, I want to start the unified API before Installation Setup, so that I can create or join through the app.
2. As an operator, I want the app to present Create and Join, so that terminal provisioning is not a prerequisite.
3. As an operator, I want Create to generate internal settings and credentials, so that I do not assemble service infrastructure manually.
4. As an operator, I want to supply an initial administrator name and password through protected UI input, so that a new Installation has deliberate administrative ownership.
5. As an operator, I want Join to accept a trusted peer choice and authenticate its identity, so that I join the intended Installation.
6. As an authorized User on an existing Node, I want to approve or reject the exact joining offer through the app, so that discovering a peer does not grant membership.
7. As an operator, I want both flows to install the Node CA into OS trust with required consent, so that HTTPS uses native system trust.
8. As an operator, I want secure-provider, trust-installation, or HTTPS verification failures to remain visible, so that failure cannot silently weaken security.
9. As an operator, I want a setup status distinct from complete readiness, so that a running listener is not mistaken for a usable Node.
10. As an operator, I want setup to establish usable identity and service state without a separate serving command, so that I can immediately make properly authenticated API calls.
11. As an operator, I want interrupted Create or Join to reuse retained identities and intent, so that retries do not produce duplicate members, signers, Clients, or grants.
12. As an operator, I want cancellation to leave an explicitly incomplete, recoverable state, so that partial work cannot masquerade as completion.
13. As an operator, I want conflicting retries to be rejected, so that an existing create/join intent cannot silently change purpose or peer.
14. As an operator, I want concurrent setup requests coordinated, so that two app actions cannot provision divergent local identities.
15. As an operator, I want completed Nodes to reopen offline, so that normal startup does not depend on another Node or central authority.
16. As an operator, I want missing or malformed retained credentials to fail closed, so that startup does not overwrite a damaged Node with a new one.
17. As an operator, I want explicit local reset when appropriate, so that recovery does not require hidden profile or keyring changes.
18. As an Application User, I want protected API operations to enforce authentication and authorization throughout setup and normal use, so that setup access is never resource access.
19. As an operator, I want the UI to remain part of the app, so that the API host does not acquire a parallel frontend server.
20. As a maintainer, I want app and CLI setup to reuse the existing lifecycle and owner APIs, so that authorization and persistence rules do not diverge between entry points.
21. As a web operator, I want the same app to Create/Join using only APIs, so that Tauri is not a deployment prerequisite.
22. As a web operator, I want to deploy owner APIs independently or the unified API, so that setup does not dictate my service topology.
23. As an operator, I want initial setup callers authorized before an administrator exists, so that another caller cannot claim my unconfigured services.
24. As a web operator, I want trust prerequisites handled by the deployment environment, so that the browser is not expected to perform privileged OS installation.
25. As an operator creating a fresh Installation, I want only schemas and the necessary initial identity/policy records created, so that setup does not synchronize nonexistent application data.
26. As an operator, I want Storage to start with an empty resource catalog, so that installing a Node does not create unwanted resources or duplicate identity/policy state.
27. As a maintainer, I want initialization and serving to share already-open owner handles, so that setup does not repeatedly reopen stores, run schema initialization or reconstruct runtimes.
28. As a maintainer, I want bundled composition to use owner-local calls and independent deployment to use authenticated HTTPS where needed, so that transport requirements do not become redundant local ceremony.
29. As an operator joining an Installation, I want approved public identity/policy imported separately from resource content, so that offline authorization works without copying unrelated application data.

## Implementation Decisions

### Owner responsibilities and minimum seed

| Owner      | Responsibility                                                                                                                           | Fresh Create work                                                                                                                                              |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| IdP        | Users, credentials, Applications, OAuth Clients and token-signing identity/trust; no Device/endpoint authority                           | Required schema; initial administrator User/credential; necessary Application/Client registrations, public login Client and protected token-signing capability |
| Management | Devices, endpoint-ID bindings, User ownership, approval/enrollment, transfer/revocation, roles, permissions, restrictions and selections | Required schema; explicit initial administrator grants; approved initial Device/endpoint binding and only necessary policy, with empty selection               |
| Storage    | Resource catalogs, User/Application namespaces and resource lifecycle                                                                    | Required local schema/store and authentication/service bindings; empty resource catalog, no seeded databases/filesystems or identity/policy objects            |

- **Management owns Devices, endpoint-ID bindings, User ownership, approval/enrollment, transfer/revocation, grants, restrictions and selections — including endpoint identity and endpoint-ID authorization.** IdP owns Users, credentials, Applications, OAuth Clients and token-signing trust — not endpoint/Device authority. Storage owns resources and consumes current Management endpoint authorization.
- **Endpoint ID identifies a transport peer; possession of its private key authenticates that endpoint, not its permissions.** Management's current approved endpoint binding and exact Device policy decide admission and resource access. Endpoint ID, Device ID, OAuth Principal and token signer are distinct. Approved endpoints do not need individual IdP token signers or full Node enrollment.
- **For independently deployed IdP and Storage: only the endpoint ID (and its Management-approved binding/policy) matters for authorization.** Storage does not need its own endpoint identity beyond receiving current Management authorization via its service Client; it does not create Devices, endpoint IDs, or duplicate policy objects. IdP does not own endpoint IDs; Management does.
- **No multi-endpoint Node abstraction, per-service enrollment ceremony, copied endpoint keys, or cross-owner database opens.** Separate HTTPS addresses/processes do not automatically create Devices/Nodes/Installations.
- **Endpoint ID identifies a transport peer; possession of its private key authenticates that endpoint, not its permissions.** Management's current approved binding and exact policy decide admission and resource access. Unknown, pending, revoked, mismatched or unauthorized endpoints deny; approval alone does not grant resource access. Storage obtains Device/endpoint authority from Management, locally when bundled or through authenticated HTTPS when independent, not from IdP Device lookups or signer-membership inference.
- **Token signing and transport identity are separate.** IdP retains the signing keys/trust needed to validate token issuers and Principals. An IdP signer record is not a Device approval, and an approved endpoint need not have its own IdP token signer or full Node enrollment. Preserve any required association through explicit owner contracts without equating signer ID, Device ID, endpoint ID or process identity.
- **Deployment topology does not create domain identities.** Separate HTTPS addresses, processes or service stores do not automatically create Devices, Nodes or Installations. Register actual transport endpoint bindings through Management only where required. Do not invent a multi-endpoint Node aggregate, copy endpoint private keys or require a separate Device/Node enrollment ceremony per API process to preserve the current IdP coupling.
- Opening/migrating an owner store is not Installation enrollment or domain provisioning. Do not require each owner to implement a separate Create/Join ceremony merely because it has a store. Storage needs valid service configuration/trust and any required credentials, not a domain-enrollment phase.
- Seed semantic objects through their owners in owner-local batches/transactions where supported. Separate stores do not imply distributed transaction guarantees. Schema/catalog/index/CRDT rows are legitimate persistence details, but do not justify repeated initialization or full-history synchronization on fresh Create.
- Register confidential Clients for actual authenticated service relationships, not one per context or a mandatory historical count. The current four relationships and separate public login Client are implementation evidence, not a fixed seed-count acceptance rule. Retain distinct least-privilege credentials where relationships are required; the operator/browser does not assemble or receive raw infrastructure secrets.
- Audit User/Client-specific key creation against the actual current token/encryption contracts. Keep material that is required for signing, encryption or retained recovery; do not retain legacy key setup solely because an older provisioning path did it. This is not authorization to remove cryptographic protection without tracing its consumers.

### Minimal lifecycle and deployment composition

- Distinguish host startup from Installation Setup and Node readiness. Starting a local listener is not an Installation-creation action, membership approval, initial permission grant, or completion signal.
- There is one existing app, deployed as desktop with Tauri/bundled services or as web without Tauri using only APIs. API hosts own service composition/lifecycle; the app owns UI assets and interaction. Do not serve UI assets from the unified API or build a second frontend.
- Support independently deployed IdP, Management and Storage APIs as well as unified composition. Define owner setup contracts and their coordination without cross-context repository access; do not make unified-only or native-only setup an architectural prerequisite.
- Ordinary startup, including the existing development unified invocation, must support a genuinely fresh host without a prior CLI Create/Join. Manual config remains optional rather than the ordinary UI prerequisite.
- Derive and securely retain local listener/settings, independent endpoint identity and protected local prerequisites as needed. Generate Installation-specific state only at the correct explicit Create/Join boundary. Join must retain the authenticated peer's Canonical Issuer, not prematurely invent its own Installation issuer.
- Preserve stable settings, independent private signers, separate IdP/Management/Storage/endpoint roots, secure credential storage, and public login Client provisioning. Never expose raw relationship secrets, private keys, passwords, or tokens through status/config responses or logs.
- Reuse owner behavior, authenticated issuer discovery, purpose-specific pairing, enrollment approval and owner-local persistence. Reuse does not require preserving the current wrapper/journal hierarchy: replace and delete redundant orchestration instead of wrapping it. Keep one app-facing Create/Join flow and minimal observation/recovery/cancellation; internal phases do not automatically deserve public routes.
- Fresh Create opens the required owners, initializes schemas and writes the minimum explicit seed locally. It does not require a reachable peer, public-history export/import, mesh admission refresh round trips or resource-content synchronization. Join separately imports the approved public identity/policy state required by the existing offline-first contract; resource discovery/content sync remains governed by normal selection and authorization.
- Open and initialize each owner once per runtime lifecycle, then pass its existing handles through seeding, specific readiness checks and serving. Do not repeatedly reopen the same store or rerun schema initialization for administrator grants, Device policy, verification and runtime construction. Legitimate stopped reopen remains existing-only and must not reseed.
- Bundled/unified composition uses direct owner-local interfaces for local provisioning and local authorization, with the same domain checks. Do not force HTTP/OAuth self-calls or remote service credentials merely to call a co-located owner. Independently deployed owners retain authenticated HTTPS relationships and owner-local persistence; do not solve remote composition by opening another owner's database or weakening normal exposed-route authorization.
- Keep the smallest durable state needed for exact retries, protected-key/reference integrity, safe cancellation and completion. Remove duplicated intent/progress/completion records when they encode the same fact without an independent owner obligation. Do not trade this simplification for silent regeneration, repair or cross-owner state access.
- Reconcile native setup commands with shared API-driven setup behavior. Web Create/Join must work without Tauri, parent-child process ownership or a local IPC-only transport. App requests must address the intended deployed services/stores rather than accidentally provisioning a separate desktop Node.
- Expose HTTPS setup/status contracts usable by the web app. Before implementing privileged mutations, define and qualify initial-setup caller authorization when no administrator exists, its lifecycle and protection against competing callers. Existing native trust may support desktop, but cannot be the web solution. Do not prescribe new operator-supplied internal secrets/configuration or an alternate enrollment mechanism without an explicit design decision.
- User-approved admission: the host automatically generates a 256-bit setup code. The operator retrieves it through protected host/deployment management and enters it in the app; never expose it in public status, URLs, ordinary logs or automatic console output. Submit it only in an explicit HTTPS `Authorization: Setup <code>` header, separate from OAuth bearer authentication. Keep browser handling transient, with no cookie/localStorage/sessionStorage persistence.
- Retain this host-local capability in dedicated owner-only protected state, distinct from public host settings and from secure-provider-backed domain keys/secrets. Bind a validated nonsecret exact operation identifier durably before mutation, serialize provisioning, preserve exact retries through cancellation/restart, and retire the capability after verified completion. Missing/corrupt state denies without regeneration. Retirement of admission is not a global normal-API enable switch. Independent owners must qualify their own admission/coordination; one service's code cannot silently authorize another service.
- Let a caller with current host setup authorization recover the exact retained nonsecret operation after browser reload, then verify current owner scope/status before adopting it. Recovery does not resume mutation or expose passwords, keys or codes; each subsequent mutation carries its own authorization. Retired admission denies recovery. Complete owner provisioning with unretired admission remains unfinished after restart and supports authorized exact finalization, not identity replacement or automatic repair.
- Network reachability, first-request arrival, loopback, TLS, CORS and public CA possession alone are not setup authorization. Specify browser origin/CSRF protections where applicable without treating them as caller identity. Initial setup admission is distinct from ordinary User authentication and from authorized peer approval during Join.
- Expose minimal setup status sufficient for the app to distinguish awaiting choice, incomplete retained setup, failed setup, and ready state. Use existing setup/readiness contracts where appropriate; do not equate a completion marker or listener with current owner trust and signing capability.
- Existing normal protected APIs always enforce authentication and exact actor/action/target authorization; without valid evidence requests deny regardless of setup status. Preserve fail-closed behavior for operations that genuinely require missing owner state. Do not add redundant global route-enable flags or blanket setup gates; readiness checks must name the specific invariant they protect. Existing public protocol routes retain their intended admission.
- Both flows require OS-level CA trust installation and verified production HTTPS across the selected service topology. Desktop coordinates native trust/elevation consent; web uses deployment-managed trust installation and ordinary browser TLS verification, not privileged browser operations. Preserve secure-provider failure handling; no plaintext, application-only CA or browser-only NSS fallback. Trust removal/reset remains explicit.
- Keep security prerequisites, domain seeding, runtime construction and integration qualification distinct. Local setup performs the checks needed to establish current owner invariants; it does not run a full HTTP token/health/service-call qualification suite as part of provisioning. HTTPS trust verification remains required. Measure and remove repeated schema/catalog/history/readback work instead of hiding it behind asynchronous acceptance.
- Setup operations are host-owned, not HTTP-request-owned. After authorization and durable exact intent binding, return `202 Accepted` without waiting for owner provisioning; the app observes completion through setup status. A closed request/browser does not cancel accepted work. Cancellation is an explicit authorized operation; host shutdown still coordinates cleanup. Keep runtime readiness checks local and specific; full service-relationship HTTP qualification belongs in integration tests, not a synchronous Create request.
- Serialize conflicting setup operations and coordinate cancellation/shutdown. Retry resumes the exact retained operation; conflicting purpose, peer, or identity is rejected. Do not erase invalid state, auto-reset profiles, migrate old intents, or rotate credentials to make startup succeed.
- Complete provisioning within the running service lifecycle without a second serving command or authentication-mode transition. Unified/desktop composition retains one HTTPS listener, prefixes once, one shared endpoint/router, independent handler admission and coordinated shutdown. Independently deployed owners retain their own listeners/lifecycles; do not impose one global listener on separate services.
- Completed restart uses persistent locally trusted state, restored endpoint admission and protected credentials without a reachable peer. Revocations and resource authorization retain existing offline-first semantics.
- Keep optional explicit CLI Create/Join as alternate host entry points only where useful; they are not an operator prerequisite for app setup. Remove obsolete completed-only startup guards and documentation rendered incorrect by the new lifecycle.
- Update operational/API/security/design guidance and affected client contracts together. Generate clients through existing owner workflows when actual public contracts change; do not hand-edit generated clients or advertise nonexistent routes.
- Simplify the existing lifecycle before extending independent-owner setup or adding further phase-specific interfaces. Assess complexity, risk and priority; name the owner of every retained seed, key and durable progress fact. Main risks are privileged setup admission, issuer choice before Join, trust/provider failure, duplicate lifecycle ownership, incorrectly publishing partial readiness and accidentally replacing local authorization with a remote dependency.

## Testing Decisions

- Test externally observable behavior at the production setup API seam consumed by the existing app, using real local IdP/Management services, public persistence APIs, authenticated Iroh and isolated Node stores. Cover web operation with Tauri absent and desktop reuse of the same owner behavior. No new per-module test framework is required.
- Agreed lifecycle: fresh API startup → app/API setup status and authorized Create/Join → verified persistent service state → authenticated use → stopped/offline reopen. Exercise unified and separately deployed owner composition with representative fixtures, not a deployment/platform Cartesian matrix. Native/API tests prove their seams, not rendered GUI interactions.
- Prior art includes existing production HTTPS Create/Join/approval/rejection/offline-reopen regression, native setup/localhost tests, credential-bootstrap/TLS tests, and pairing generation/offer invalidation race tests. Reuse their fixtures and bounded execution rather than duplicating all previously qualified owner matrices.
- Prove fresh startup succeeds without retained domain credentials or CLI provisioning and reports incomplete setup. Normal protected requests without valid authentication/authorization deny before and after setup; assert concrete missing-state refusal rather than a blanket route toggle.
- Prove owner boundaries at the existing app/API seam: Device/endpoint creation, lookup, approval, transfer and revocation are Management-owned; IdP owns User/Client identity and token-signing validation, not an alternative Device authority. An approved endpoint without an IdP signer record must be usable when its exact Management policy permits; a valid OAuth token or signer alone must not approve an unknown/revoked endpoint. Cover the same behavior in unified and independent composition, including learned denial on existing connections and offline reopen.
- Prove fresh app/API Create establishes only the necessary initial administrator, explicit permissions, registrations, Management-owned Device/endpoint trust and IdP token-signing capability, permitting valid authenticated operations without another serving command. Start with peers unavailable; assert no peer-history/content exchange, no seeded Storage resources and empty resource selection. Check semantic owner state, not hard-coded counts of implementation catalog/CRDT rows.
- Verify required stores/schema initialization and runtime construction are not repeated within one lifecycle. Prefer existing owner seams and lifecycle observations to a new instrumentation framework. A stopped offline reopen must reuse identities and state without seeding again.
- Record fresh Create and Join timing separately, with schema/open, credential/password/key work, semantic seeding, public-state import and serving phases distinguished. Report build/profile and external provider/trust costs separately. Async acceptance latency is not initialization completion latency. No new arbitrary latency SLA, cache, timer or benchmark framework is implied; unexplained repeated work and known failures remain blockers.
- Prove app-driven Join authenticates the chosen peer, discovers the correct issuer, requires authorized approval, retains independent local identity and establishes the concrete owner invariants needed for offline operation. Qualify required public-state import independently from fresh Create and from resource-content synchronization. Rejection, malformed/stale offers and an unauthorized setup caller cannot complete setup.
- Test actual HTTPS setup admission, unauthorized/competing caller denial, applicable browser-origin/CSRF protection, retry and loss/invalidation of setup authorization. A mocked admission callback or native-only test cannot qualify web setup. Source Join approval remains subject to ordinary authenticated User permissions.
- Prove prompt durable acceptance, observable completion after submitting-client disconnect, explicit authorized cancellation and host shutdown. Acceptance is not completion. Measure initialization stages without secrets; remove redundant initialization/readback work rather than increasing deadlines or weakening checks.
- Prove representative interruption/retry, cancellation and concurrent-request behavior preserve stable identities and deny conflicting intents. Missing/malformed retained state must remain intact and fail closed.
- Prove both completed flows reopen offline with retained identity and normal local authorization; preserve existing learned-revocation and endpoint-admission behavior without rerunning unrelated matrices.
- Exercise representative secure-provider, OS trust-install and HTTPS verification failures with existing injected commands/isolated roots. These prove refusal and cleanup, not actual OS provider/trust installation. Do not change the real system CA store, reset profiles or modify protected provider state without explicit authorization.
- Verify unified/desktop one-listener composition, correct prefixes, endpoint/runtime ownership and coordinated shutdown; verify independent owner deployment keeps separate lifecycles and addresses. Add focused app web tests without Tauri for setup API use/errors. Mocks do not prove OS process exit or actual GUI approval.
- Use reproducible bounded Ubuntu Linux x86_64 evidence, focused relevant package/test filters, applicable formatting/Clippy/frontend/boundary checks and changed-source provenance. Run one resource-bounded Rust build at a time and record literal commands, failures, timeouts and inherited diagnostics.
- Do not increase timeouts, bypass current permission checks, or manufacture passes with weaker verification. Existing HTTPS regression timing is close to its bound; a timeout is evidence to investigate, not an automatic deadline extension.
- Do not run broad Cargo Hack feature powersets, CRAP, full-workspace/platform sweeps, or privileged native installation without renewed authorization. Report existing frontend/tooling blockers honestly.

## Out of Scope

- Serving a UI from the unified API, building a second frontend, or adding a new networking framework.
- Unauthorized initial setup, alternate Node enrollment, automatic join approval or automatic administrator grants on server start. HTTPS Create/Join and an explicitly designed initial-setup admission policy are in scope; a pre-existing administrator cannot be a prerequisite for initial Create.
- Rewriting generic persistence, mesh, pairing or filesystem owners; merging context stores or introducing compatibility migrations.
- Changing resource ownership/selection semantics or replacing explicit initial permissions with an authentication bypass. Moving Device/endpoint authority from IdP to Management **is required in scope**, including persistence ownership, lifecycle routes, setup/import/reset consumers, public-state allowlists and generated clients.
- A new multi-endpoint Node enrollment abstraction, one Node/Device per API process, copied endpoint private keys or a requirement that each approved transport endpoint possess an IdP token signer.
- New per-phase setup protocols, mandatory one-Client-per-context or fixed historical Client/key counts, a global setup framework, cross-transaction caches, or a distributed bootstrap transaction.
- Removing TLS, OS trust requirements, explicit consent, secure-provider protection, or current identity/resource authorization.
- GUI approval end-to-end certification, physical multi-device/WAN/NAT/relay validation, Windows/macOS qualification, production headless/container deployment certification, exhaustive fault/feature matrices, provider-loss recovery and credential export/import. Same-host web-without-Tauri and independent-owner/unified API behavior are in scope despite these deferred deployment certifications.
- Automatically resetting existing data/provider state or modifying real OS trust as a test.
- Commits, branches, merges, pushes or implementation as part of publishing this spec.
